# 动态审查清单 A：实现、接口与验收

日期：2026-10-04。本步对应 [三个大步骤计划](superpowers/plans/2026-10-04-dynamic-checklists.md) 的 A。检索验收已由用户交给另一位 AI；本步没有修改其部署或启用向量开关。

## 1. 产品范围

审查指标由**每个用户、每次采购的实际要求**决定，不设置采购品类白名单。水果的甜度、服装的面料、电子产品的刷新率都是示例，指标不受旧八字段列表限制。同一用户也可以为不同采购设置完全不同的清单。

每个指标包含稳定 ID、中文名称、适用品目、规则、是否启用、是否必需和设置来源。指标名称与单位可以自定义；服务端支持六种受控规则：数值/区间、金额、枚举、资料存在、期限、人工复核。规则类型有限便于后续安全判定，不允许执行用户或模型提供的程序。复杂条件暂保留为人工复核项。

资源保护：最多二十个品目、一百个指标，单份定义不超过 128,000 UTF-8 字节。这是当前接口容量保护，**尚未验收一百指标的模型时延或成本**。金额目前接受 CNY/USD/EUR，须明确计价单位和含税口径；不推断汇率或自动补业务口径。

## 2. 本步实际完成

| 内容 | 实现与边界 |
| --- | --- |
| 手工草稿 | 用户设置指标和阈值，MySQL 保存；来源为 `user_defined`，保留设置理由和服务端身份 |
| 背景原文 | 可附买方需求原句；校验同采购/快照、买方角色、真实非空原句及解析记录指纹，不伪称阈值从原文自动提取 |
| 确认版本 | 明确 `confirmed=true`、选择指标后生成不可变版本；编辑生成新草稿，历史版本仍可读 |
| 部分确认 | 未选项留在草稿；连续确认累积已选指标，返回剩余 ID；重新 PUT 替换完整草稿定义，不意外合并已舍弃的旧指标 |
| 权限与并发 | 项目查看者只读；写事务复查 owner/editor；资料 revision、清单 revision 与 actor 范围的幂等记录防止旧请求覆盖新修改 |
| 状态与来源 | 资料升版需重新确认，旧快照明确标为 historical；背景证据变更阻断读取/确认，供应商资料不能充当买方要求 |
| 运行保护 | 保存或确认时拒绝运行中的 Case；动态清单存在后，旧八字段新提问/重试/恢复返回 `checklist_execution_pending` |
| 删除 | Case 清理按操作记录→head→确认版本→快照顺序移除，包含部分确认的基础版本外键 |

幂等回放返回该操作当时的结果，后续状态请 GET 最新清单；回放仍校验当前写入权限、资料 revision 和删除状态。确认不是后台自动行为，也不直接修改供应商事实。当前项目权限沿用现有项目成员共享可见性，未新增成员间私有清单功能。

## 3. 数据和 API

- `checklist_heads`：每个 Case 的草稿、修订号、确认版本与部分确认基础版本指针。
- `checklist_versions`：不可变定义、资料快照/修订号、来源绑定、指纹、确认身份和理由。
- `checklist_operations`：按 Case/身份/操作/幂等 key 隔离的请求指纹与结果回执。

数据库迁移：`0014_dynamic_checklists`，新增三张表，无历史八字段结果回写。

| 方法 | 路径 | 含义 |
| --- | --- | --- |
| GET | `/api/v1/cases/{case_id}/snapshots/{snapshot_id}/checklist` | 草稿、确认版本、问题、资料/清单修订号、是否当前快照、执行接入状态 |
| PUT | 同上 | 提交完整草稿定义，需两个预期修订号、理由和 Idempotency-Key |
| POST | 上述路径 + `/confirm` | 用户明确确认选定 ID；不能确认未知、停用或有未解决冲突的指标 |
| GET | `/api/v1/cases/{case_id}/checklist-versions/{version_id}` | 按项目权限读取指定历史确认版本 |

例如苹果甜度要求是如下定义；服装或设备使用相同契约，替换名称、品目和适用规则即可，不要求先登记品类。

```json
{
  "items": [{"item_id": "apple", "name": "苹果"}],
  "criteria": [{
    "criterion_id": "brix", "item_id": "apple", "name": "甜度",
    "rule": {"type": "numeric", "operator": "gte", "value": "12", "unit": "°Bx"},
    "source": {"kind": "user_defined", "reason": "本次采购要求"},
    "required": true, "enabled": true
  }],
  "expected_revision": 1,
  "expected_checklist_revision": 0,
  "reason": "设置本次采购指标"
}
```

修订冲突返回 409，应重读并核对变更后再保存；无权限资源仍返回既有的 404，避免泄露资源是否存在。未解决重复名称/金额口径等问题可保留草稿，确认受影响的集合会被拒绝。纯人工项及带未解释条件的项保留 `manual_review_ids`，不能作为自动满足处理。

## 4. 审查与修复

先执行失败回归再实现与修复，覆盖超过八项、多个用户/采购独立清单、同名不同品目、部分确认累积及替换、快照升版、撤权、来源串 Case/快照/供应商、无原文空白引用、失败事务无残留、删除清理及旧执行器保护。

独立代码审查发现并修复三类具体问题：

1. 空白 quote 归一化成空串后会匹配任意原文；契约和仓储均拒绝空白引用。
2. 资料升版后 GET 旧快照仍显示当前确认；现在返回 `is_current_snapshot=false`、`state=historical`。
3. MySQL 并发事务的旧一致性视图可能漏掉刚保存的清单；Case 锁内改用清单 `FOR UPDATE` 当前读。两条真实并发回归在修复前分别错误地产生新 Run/重试，修复后均拒绝。隔离语义已核对 [MySQL 8.4 官方一致性读文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

复核了回滚后幂等兜底的授权、删除和快照检查，防止通过异常兜底绕过写入约束。

验收记录：

- 定向离线清单/API/迁移 metadata：**36 passed**。
- 真实 MySQL 清单 3 项 + 原运行仓储 5 项：**8 passed**；包含双连接覆盖更新、部分版本重开恢复、外键清理及两个明确的事务交错场景。测试 outbox 使用独立事件类型，不触发运行服务的 worker。
- 实际数据库 head：**0014_dynamic_checklists**。
- 完整离线回归：**924 passed / 32 skipped**，网络尝试 **0**；Ruff / `pip check` / `git diff --check` 通过。外部服务测试按设计跳过，真实 MySQL 8 项为另外显式启用执行的结果。可检查 [结构化验证报告](../data/verification/dynamic-checklists-a-2026-10-04.json)。
- 独立审查修复后复查：未发现本步范围内剩余 P1/P2 阻断项；审查者另跑相关四项离线回归通过，未重复连接 MySQL。

## 5. 下一大步骤及尚未接入的能力

**下一步 B**：Agent 从买方需求/订单提出候选，校验原文和规则，用户修改/确认；通用事实绑定 criterion_id 和品目，确定性核验，Run/记忆/结果/修正/导出绑定清单版本。完成后接入新的动态执行器。

本步只有手动清单 API，**没有实现订单自动提取或动态指标端到端核验**。`execution_available=false`，动态 Case 暂时被保护性阻止进入旧执行器。新功能尚未连接前端，也没有重启旧 API/Celery 或调用真实大模型。不同品类的业务质量与性能成绩需要在 B/C 验收，旧设备样例成绩不扩展为所有采购场景成绩。
