## 实际记录核对

只读核对目标会话的消息、Run、attempt、固定基准、候选及保存确认操作。完整对话副本仅在被忽略的本机 `data/verification/chat-2026-10-09/`，没有提交聊天正文、凭据或环境文件。

- 最初两次数量候选均包含 20 台，但基准为空，均未单独保存。后续七项候选仍绑定空基准，仅包含七个 manual 方向，没有数量；随后只发生一次保存、一次确认，确认版本确实没有 20 台。
- 七项分别是机型/规格、配置下限、交付要求、价格与付款、质量与售后、资质与证明、验收方式，属于待明确的人工核对方向，不能解释为已明确的数值或供应商承诺。
- “补充采购文件、供应商报价、承诺材料”失败 Run 的六个历史 attempt 均为模型调用 0；之后日期问题的失败 attempt 同样为 0。记录不支持把此故障归因于 DeepSeek 返回错误。
- 原工具定义上界为 11949 字节预算单位。原七项固定基准与短问题即使不带历史及摘要，上界仍达 16010，超过 standard 的 16000。这里是含开销的保守序列化字节上界，不是服务商实际 token 数，也不是模型声明窗口。
- `_messages()` 原来等待 `fit_decision_history()` 抛出异常，再移除可选记忆；但该函数返回超限的必需消息，由后续 `Budget.reserve()` 拦截，因此回退路径不会执行。
- 读取当前状态时，早期候选基准修订为 0，确认后的清单修订为 2，将早期卡片标为历史有合理版本依据。数据库不能还原首次渲染瞬间的页面时序，本步不宣称已查明“刚生成就历史”的 UI 根因。

## 修复内容与边界

1. Assistant 专用工具 schema 只删除展示用的字符串 `title`，保留名称、说明、默认值、判别、必填、额外字段限制、长度/模式/数量约束及全部 `$ref`。原 Pydantic 与 JSON Schema 校验继续执行，未修改通用 DynamicAgent 或 Provider 契约。
2. 基准和资料 JSON 紧凑序列化。历史按完整问答轮裁剪；若仍超限，逐步移除可选摘要条目、摘要 ID、偏好，并重新尝试组装。固定基准、当前完整问题和不可信上下文提示始终保留。
3. 必需上下文仍超限时继续在模型请求前拒绝，给出中文解释，明确直接重试同一问题不会缩短上下文。没有扩大预算、截断规则或自动重试。
4. 持久化 `assistant_context` **首轮组装审计**：预算、选中/省略轮数与摘要数、偏好数、是否必需上下文超限。只含数字和布尔值。检索后的后续请求仍受预算保护，但本字段不代表逐次模型请求审计。
5. SYSTEM 补充采购准备指引：未知指标不编造阈值，候选必须保存确认，文字要求不强制重复上传；没有供应商资料时先补资料，不能声称已能判断满足，也不主动邀请立即审查。指引属于模型行为约束，真实模型遵循程度仍须另行实测。

本步没有自动把 20 台写入已确认版本，没有保存或重试目标会话，没有变更指标、供应商、资料或修正记录。未保存候选承接需要下一步独立设计和版本约束测试；当前提示说明不等于已经解决该问题。
