# M2-1：核验答复的来源范围与冲突追问（2026-09-26）

本步修正同一 Case、同一快照的 A 供应商核验答复混入 B 供应商来源的问题，并让“哪两处判断冲突”的追问聚焦实际矛盾来源。只改内存核验答复边界；没有读取 `.env`、启动 Docker 或调用 DeepSeek。

## 已实现

- 正式核验答复只接受当前快照中的一个结果，并核对字段为内存。旧 `partial` 与新 `complete` 结果或 A/B 两家结果不能拼在同一答复；跨供应商矩阵留到 M2-6。
- 模型额外提交的证据 ID 必须属于该核验结果已验证的证据集合。即使 Agent 在同一会话中读过 B 的报价，提交 A 的核验结果时也不能引用 B 的原文。原始资料读取工具的范围保持现状，限制发生在生成正式答复时。
- 内存规则在结果中分别保留完整证据链和结论理由相关的证据。包括“根据哪两处判断？”在内的冲突来源追问展示报价与规格书；一般达标问题继续展示需求及供应商资料。模型额外提交需求来源也不会使冲突追问偏离两处矛盾资料。
- 冲突来源追问必须关联已验证的核验结果；仅提交看过的原文不能冒充对既有结论的解释。

## 离线验收

在 `docucheck` Conda 环境，后端测试 **110 项通过**；全目录 Ruff 通过，`pip check` 无依赖冲突。新增回归先复现失败、再验证修复：A 结果加已读取的 B 报价被拒绝；A/B 与同供应商新旧结果 ID 混用被拒绝；非内存字段不能由内存答复渲染器输出；不带核验结果的冲突来源追问被拒绝；“你根据哪两处判断冲突？”和“根据哪两处判断？”均只显示报价与规格书。已有 M1 两轮 Agent、内存规则用例继续通过。

这些是离线脚本和规则测试，没有再次运行真实 DeepSeek 对话。模型在修正后的引用约束下是否一次选对工具与证据，留待后续用户执行的真实模型验收。

## 边界与下一步

当前核验答复仍限内存字段的一家供应商。没有关联核验结果的普通原文问答仍依赖 Agent 选源，尚未将用户自然语言提及的供应商强制绑定到引用；其通用作用域要与 M2-6 多供应商矩阵及 M2-7 指代机制一起设计和验证。复杂 PDF/XLSX 内容的解析覆盖仍在 [M2-2](m2-task-breakdown-2026-09-25.md) 处理。前端工作继续遵守先讨论设计规范与样式的暂停点。
