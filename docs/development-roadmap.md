# DocuCheck 开发计划（讨论稿）

日期：2026-09-24。依据《DocuCheck-AI开发协作交接文档-v1.0》以及需求规格 v0.1、架构 v0.4 制定。本文件是实施建议，不代表功能已完成，也不替代原需求的验收门槛。

## 目标与边界

交付本地单用户的笔记本采购资料初审工作台：一份需求、每家一份报价和一份规格书、最多三家供应商；覆盖八字段和五类业务状态；每个确定性结论可回到原件；支持修正、重算、历史运行和报告导出。保持既定技术栈，除非兼容性、质量、性能或许可证检查给出调整证据。

## 开工前需补齐的约定

1. **样例与标注先行。** 先制作一套完整的模拟文档包，覆盖 PDF/XLSX、正常结论、资料冲突、证据不足、待人工确认和不达标；同时定义标注格式。之后扩展至至少 12 组、104 条判例，其中至少 6 组独立封存用于最终验收。每组可有多家供应商，应明确判例计数单位为「供应商 × 字段」，并记录每份文件的授权来源。
2. **证据与覆盖契约。** 为每个文档记录解析状态、成功覆盖范围和失败原因。事实证据需固定 `document_id`、解析版本、页码/工作表单元格、原文和值；需求与供应商事实的适用型号、字段口径要可核验。解析失败时，相关字段不得进入正常的“证据不足”或“满足”路径。
3. **有争议语义的判定表。** 在编码前写出八字段的典型反例：含税与未税、交期起算事件、已装与最大支持、主机与包装重量、约等于、型号不一致、同一文件内矛盾。人工修正只能基于可定位原文更正事实，不能直接改最终状态。
4. **模型使用边界。** 决定可发送资料的范围、模型服务的配置方式与凭据管理；开发和 CI 用 Fake Provider，真实模型只用模拟或获准资料。记录模型 ID、提示词版本、超时、重试次数和每次调用成本/耗时。此项在接入真实 Provider 前确定即可。
5. **评测口径与失败处理。** 在结果生产前冻结准确率、证据定位率和性能测量脚本的分母定义；明确 `partial/failed/interrupted` 与五类业务状态的关系。所有失败和超时均纳入性能统计，不以未处理字段充当缺失字段。

## 阶段与完成条件

| 阶段 | 主要工作 | 可检查的完成条件 |
|---|---|---|
| 0. 环境与固定样例 | 确认 Git、Python 3.12 隔离环境、Docker Linux Engine、E 盘挂载、MySQL 3307、Redis、worker；制作第一套模拟 PDF/XLSX 与标注 | 一条命令能启动基础服务，健康检查和挂载读写通过；样例的原件与预期证据可人工核对 |
| 1. 解析与证据 | PDF/XLSX 输入校验、限额、解析适配、覆盖状态、原件定位；开发集比较 MinerU Basic 与 Flash | 样例中全部八字段的原文位置可复核；失败能定位到文件和阶段；解析配置有测量记录 |
| 2. 事实与规则 | 事实 schema、证据引用校验、单位换算、五状态规则；Fake Provider 与配置化真实 Provider | 固定判例通过；无证据、口径不清、资料冲突和解析失败均不能误判“满足” |
| 3. 运行后端 | Case/文件/Run API、MySQL 迁移、Outbox、Celery 幂等、修正和重算、版本快照 | 单供应商三文件流程可运行；重复投递、超时、取消和中断有可复现结果 |
| 4. 工作台与报告 | Vue 页面、结果矩阵、PDF/XLSX 证据查看、修正、历史、XLSX/JSON 导出 | 用户从空任务完成上传到导出；页面和导出读取同一运行快照 |
| 5. 独立验收与交付 | 扩充并封存验收集、质量/性能测试、CI、README 和失败案例 | 报告公布准确率、证据定位率、危险误判数、耗时分布及分母；干净环境可复现 |

阶段 0～2 优先形成一个“需求 + 一家供应商”的纵向闭环，然后扩到三家。估算沿用架构文档的 150～190 小时；任何阶段的未达标项应记录证据和影响，不把目标当实测成绩。
