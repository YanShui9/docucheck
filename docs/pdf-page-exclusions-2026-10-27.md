## 范围如何生效

用户在既有资料关联弹窗内查看完整单页原文，选择另一 SKU 的身份锚点并填写原因，最后明确确认该页不属于本次采购，也不含适用本次采购的共同条款。服务端重新展开全页来源并校验原件、解析版本、完整页、买方与供应商 SKU、身份锚点、关联重叠、混合型号及有限共同条款。未知、部分解析、目标型号和混合范围继续拒绝；这些有限规则不证明任意自然语言语义无关。

排除范围以不可变关联 `schema_version=2` 保存。`dynamic-rules-v16` 在完整库存核对时接受有效排除页；模型抽取与事实引用仍只允许原已关联范围。此次排除共 2 页、10 个原文块，抽取所选 35 个原文块与排除前相同，排除页不作为已核验事实。v16 保留 v15 的金额与材料判断；v15 及更早规则拒绝 schema 2，旧 schema 1 的合同和固定身份保持。

有排除版本的保存和撤销必须传完整列表及严格布尔确认，取消最后一项创建新 schema 1；旧客户端不能静默删除排除。清单重新确认后不自动续用旧排除。草稿离开保护、跨文件保留、未知保存沿原幂等键重试，以及忙碌与权限状态均沿现有合同处理。

报告与 JSON 使用 Run 冻结版本，展示文件、页码、其他 SKU、原因、全页原文、确认人和时间；Excel 增加“范围排除”表，每个原文块一行，避免拼接整页截断。旧导出不增加空排除记录。

## 此次未通过的原因与下一步

供应商 A 的工具事件记录 `candidate_invalid`，两条候选被 `material_sources_overlap` 拒绝，无语义修复或人工重试。供应商 B 的批次成功，因此该供应商的 4 项在持久化规则结果中局部 complete；整个 Run 为 partial 时，既有 API 将全部正式标记降级为 false，JSON 和 Excel 同样显示非正式，不能作为完整审查结论。

只读重建实际 Run 冻结的 schema 2 版本后，两家库存覆盖均为 true；所选抽取原文仍为原来的 35 块，排除的 10 块不进入抽取、事实引用或普通导出来源。排除范围已生效，但它不保证模型候选结构正确。现有持久化事件没有保存被拒绝候选的原始 JSON，仅凭错误码与计数不能还原具体重叠结构或确切历史根因。后续优先补材料候选的有界可诊断信息及可复现反例，再决定修复与单独复测；本步不放宽来源守卫，也未为获得成功结果重新发送模型请求。

验收脚本最初遗漏 partial 下的公开正式标记降级，并把 Excel 文本页码与 JSON 数值页码直接比较；均按既有产品合同修正后只读重跑。正式出口标准仍是 completed 且 8 项 complete/formal，本次机器摘要明确保留 `formal_review_acceptance_passed=false`。

早期红测、失败和主动取消的全量运行均保留，不计入通过。第 04 次完整门禁在 93% 时触发原 1200 秒运行时限，未观察到测试失败；保留该未完成报告，随后仅将本次 ignored runner 的 pytest 等待上限延长为 3600 秒，仍执行原完整测试范围、环境清理与离线网络守卫，产品与测试断言均未改。最终全量前，4 个旧测试仍断言当前默认 v15；已先复现失败，再只更新默认版本断言，104 项相关回归通过后重启冻结门禁。前端首次构建的测试类型错误、早期测试设置错误和验收脚本全角冒号假设也单独保留。最终产品源码不据这些工具错误放宽。
