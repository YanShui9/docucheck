# M2-2a：PDF 源文字覆盖校验（2026-09-26）

本步只修正 PDF 原件中的可提取文字被 MinerU 中间结果静默漏掉、却被标为 `complete` 的问题。没有调用 DeepSeek、启动 Docker、安装依赖或修改前端。M2-2 其余解析覆盖与任务限额仍未完成。

## 已实现

- `parse_pdf` 在读取 MinerU 中间结果后，用 pypdf 再读原 PDF，逐页比较可提取文字行与该页证据块。比较时做 Unicode NFKC 归一化并忽略空白；同一段解析文字只能匹配一条源文字行，重复行不能共用一次命中。
- 某条源文字行找不到对应解析文字时，记录 `page:<零基页码>:source_line:<提取文本的一基行号>:not_extracted`，把文件标为 `partial`。缓存入口无法提取某页源文字时也标为 `partial`；直接 PDF 解析入口仍拒绝纯扫描或空白页。页数不一致则解析失败。原有 MinerU 不支持块和其他覆盖问题仍保留。
- 开发模拟包的哈希绑定解析缓存经 `load_case` / `bind_document` 进入证据仓库时，同样对原 PDF 做覆盖校验。这样缓存即使自身哈希正确，也不能因漏掉原文字段而生成完整核验结果。解析版本增加 `/source-text:1`，新快照的证据 ID 随版本变化。

## 离线验收

新增用例先复现两条正式入口的漏抽误判，再验证修复：直接 PDF 解析漏掉“已装内存至少 16 GB”；模拟包缓存漏掉同一句且重新写入合法缓存哈希；模拟源 PDF 提取文字包含两条相同内容而解析结果只有一条。三种情况均保持 `partial`，缓存用例的内存规则不发布业务结论。既有解析、证据与 Agent 回归继续通过。

在 `docucheck` Conda 环境执行 `backend/tests`，**113/113 项通过**；`ruff check backend/app backend/tests` 通过，`pip check` 无依赖冲突。本步仅做本地离线验证，未重新运行真实模型对话。

## 边界与下一步

这项校验只能检查 pypdf 能从原件提取的文字。复核已用“普通正文 + 含内存规格的图片表格”混合页复现：如果 MinerU 漏掉图片，当前文字比对仍可能返回 `complete`。图片文字、扫描件、图形及表格结构和语义必须在后续小步单独处理。独立调用 `parse_mineru_middle` 只读取中间 JSON，不能单独证明原 PDF 已覆盖；正式解析和模拟包加载入口才执行源文件校验。

下一小步是 M2-2b：修正 XLSX 工作表范围声明错误时，只读迭代可能跳过实际单元格却仍返回 `complete` 的问题。之后仍需完成 PDF 非文字内容、XLSX 其他不支持结构及任务级限额，才可验收整个 M2-2。
