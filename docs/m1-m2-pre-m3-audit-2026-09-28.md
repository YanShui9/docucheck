## Agent 工程定位与面试表达

这是一套**受控的单 Agent 与规则服务组合**。普通问答由模型在 LangGraph 的“决策→工具→观察”循环中选白名单工具，证据检索为快照内词法 RAG，模型提候选事实，服务端核对原文和归属，规则引擎形成业务状态。对明确的三家八项任务，服务端把每家抽取、核验和最终提交约束为固定进度；因此这一段是 Agent 与工作流混合，不能称为完全自主规划。LangGraph 官方将预设路径称为 workflow、模型动态决定工具称为 agent；受控混合是合理工程取舍，但描述须准确。[LangGraph 官方说明](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

当前做到了原型阶段的重要环节：工具契约、上下文与来源隔离、预算、失败状态、可重放的离线测试和真实模型探针。距离可持续运行的 Agent 仍缺持久化会话/运行恢复、正式上传与异步 worker；`builder.compile().invoke(...)` 目前无持久 checkpointer，CLI 会话状态仅在进程内。LangGraph 官方把线程级 checkpoint 用于会话连续性、人机协作和故障恢复；M3 选择 MySQL 业务状态与显式 attempt 重试时，应说明它与原生 checkpoint 的区别及幂等边界。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

面试中可如实回答：为什么保留规则引擎？采购“满足”是可审计判定，模型只负责提取候选和调度；为什么暂不加向量库？当前词法开发集无漏召回证据，真实语义改写仍需独立集检验；为什么不用多 Agent？现有单 Agent 的可靠性与成本尚未稳定；怎样证明有效？给出离线回归、真实轨迹、失败案例和明确分母。不要声称 24/24 等于正式准确率，也不要声称 prompt 注入已被全面解决。主流 Agent 评测将任务、尝试、轨迹和最终结果分开，并在开发集之外做多次试验；当前项目的下一轮评测应照此补齐结果级断言、失败分母和调用/token/时延/费用。[Anthropic Agent 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[LangChain 评测类型](https://docs.langchain.com/langsmith/evaluation-types)
