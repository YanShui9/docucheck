# 连续对话候选承接修复

## 范围与设计

修复已授权的采购对话缺陷：用户先提出采购 20 台手机，再补充七个待确认方向，下一份完整候选必须保留数量。候选仍须由用户明确保存、确认；正式审查只读取已确认版本。

在现有 assistant_runs.base_json 中增加带类型标识的内部绑定封套，保留原保存清单作为 authority，并固定引用同对话最近一份完成的变更候选及其摘要。无前置候选时维持原 JSON 结构，不迁移数据库，不修改既有记录。

执行、提交结果和历史读取时重放前置候选 patch，核对原始用户消息、完整候选、diff、答案、摘要、资料快照、对话、清单版本与消息顺序。版本变化后不承接旧候选；不同对话不共享候选。最多承接 16 层，达到上限须先保存草稿，禁止悄悄丢弃前面的要求。

## 验证顺序

1. 先复现数量丢失及更新失败，再实现候选绑定和受控重放。
2. 验证跨对话、清单变更、重试、篡改、深度限制及历史只读保护。
3. 覆盖资料版本 0 的前后端候选状态；未复现的首次展示误判不擅自放宽保护。
4. 定向测试、完整离线回归、静态检查、独立代码审查，通过后本地 Git 提交。

## 边界

- 不修改用户已经确认的真实手机采购清单。
- 不调用收费模型，不重跑真实采购任务。
- 本步骤先交付并验证代码。运行中 API/worker 更新需经过闲置检查和受控重启，另行记录，不能以源码完成代替部署完成。
- 文档提取 propose_checklist 产生的候选仍沿用现有保存入口；本次只承接 propose_changes 的连续买方要求修改。

## 已验证的行为

- 合成手机对话：20 台数量候选 → 普通聊天 → 七个待确认方向，共八项；数量 ID、数值、单位及原用户来源完整保留。新增 diff 仅七项，完整候选八项；后续短问题也能完成。
- 未保存时数据库清单仍为空，无正式 checks，不能导出正式报告；用户保存并确认后，完整八项进入确认版本，旧候选按版本只读。
- 显式更新、删除沿用原 ID；重新打开数据库连接及失败重试继续使用原绑定。其他对话、上传新快照、人工保存新 head 都不继承旧候选。
- 父候选变更后的摘要与固定引用不一致会拒绝；即使重算摘要，绑定时仍重放 patch，核对实际用户指令、候选及 diff。执行前将祖先 source_digest 与实际快照比较，历史读取也检查来源。
- 达到层数上限返回明确 409，页面中文提示先保存草稿且保留输入；保存后可继续。
- 新候选 revision=0 的前后端测试均可编辑；旧版本在 head 变化后仍可读、不可直接覆盖。真实“第一次展示即历史”没有独立时序证据，不宣称修复了一个未复现的 UI 根因。

## 独立审查与修复

独立 reviewer 检查实际代码，报告并关闭两项问题：

1. MySQL RR 中普通 SELECT 可能沿用提交事务早先的旧视图，错过刚完成的上一轮。绑定及执行祖先校验改为 current read，历史读取继续只读。[MySQL 8.4 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)与实连结果一致。
2. 独立连接先锁 child 再锁 parent 可与提交路径相反。来源校验统一经 AssistantRepository._guard，先取得 Case 锁再读 Run 与祖先。

真实 MySQL 回归先建立旧视图，再让另一个 engine 完成候选，确认普通读取仍为旧值，然后要求绑定选择刚完成的候选；修前断言失败、修后通过。另以竞争连接 NOWAIT 实证来源校验已持有 Case 锁。测试仅创建独立临时任务、隔离 outbox 并清理，不触碰用户真实采购任务。新增锁断言最初误用于历史只读请求，测试夹具已纠正为只检查 current_read 路径，最终通过。

## 验收与应用状态

完整后端离线门禁 **1304 passed / 41 skipped，网络尝试 0**，Ruff 与 pip check 通过；跳过的是显式 opt-in 外部集成项，其中本次增强的真实 MySQL 用例另行执行 **1 passed**。定向后端 58 项通过，网络尝试 0；前端 **172 项**通过，类型检查和构建通过。独立审查报告的问题均已修复，最终无阻断项。脱敏证据见 [验收记录](repair-assistant-preview-evidence-2026-10-09.json)。本机服务应用结果另行记录，不能以源码通过代替运行中版本已更新。

内部封套由新代码兼容读取旧 JSON；旧程序不认识新封套。因此上线产生新绑定之后，不能盲目回退到旧程序读取新 Run，应回滚至仍兼容该封套的修复版本或向前修复。候选链有 16 层的数据库重放开销上限，不是无限对话存储；未保存候选不能跨资料版本迁移。
