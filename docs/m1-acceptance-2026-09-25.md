# M1 最小真实 Agent 验收小结

日期：2026-09-25。本文只验收 `examples/dev-pack-001/` 模拟包上的内存核验与来源追问；详细协作过程见 [分步计划](step-by-step-plan.md)，后续范围见 [开发路线](development-roadmap.md)。

## 已验证的链路

- 经哈希核验的需求 PDF、供应商 A 报价 XLSX 和规格书 PDF 进入同一不可变快照；证据保留页码或单元格位置。
- DeepSeek `deepseek-flash` 经 LangChain Provider 驱动 LangGraph 单 Agent 选择白名单工具。候选事实经来源和值校验后，由 Python 规则给出正式内存状态。
- 模拟包需求为至少 16 GB，报价为 16 GB，规格书为 32 GB；规则给出“资料冲突”，引用报价 `报价!B6` 与规格书第 1 页。追问沿用同一会话和快照，复用已验证结果并读取原文。
- 决策、抽取、工具、token 和期限使用同一运行预算；越权证据、无效答复、资料未完整覆盖及预算耗尽有离线测试。

## 实测记录

| 检查 | 结果 | 证据范围 |
| --- | --- | --- |
| 单次 Provider 工具调用 | 用户反馈 `MemoryProbe` 返回 16 GB，304 输入/35 输出 token | 仅模拟短句，不能证明 Agent 业务链路 |
| 三批内存抽取 | 用户反馈 3 次模型请求，3812 输入/308 输出 token；需求、报价、规格书分别为 16/16/32 GB，冲突结果符合原件 | 35 个模拟证据块；仅内存字段 |
| 两轮 Agent 对话 | 第三次尝试中首问 `completed`，6 次模型调用，10,342 输入/524 输出 token；追问 `completed`，3 次调用，7,019 输入/257 输出 token | 两份本机运行记录的 `conversation_id` 和 `snapshot_id` 相同；路径分别为 `extract_facts → evaluate_checks → submit_answer`、`get_check_results → read_source → submit_answer` |
| 模拟包词法检索 | 查询 `RAM`、限定 `vendor-a`、`limit=12`，三处相关内存来源找回 3/3 | 只针对这一查询与模拟包，不代表通用召回率 |
| 本机离线回归 | 后端 pytest 90/90 通过；`ruff check backend/app backend/tests` 通过；`pip check` 无依赖冲突 | Conda `docucheck`、Python 3.12；离线测试未调用模型 API |

真实两轮演示在前两次尝试中分别遇到首问 `decision_budget` 与追问 `one_tool_required`；修正上下文句柄保留和 Provider 工具选择后，第三次两问均完成。一次成功演示不能用于估计可靠性比例、响应时间或模型费用；本机运行记录保存在被 Git 忽略的 `data/agent-demo/`，不会随代码提交。

## 已知限制与后续范围

- 追问“哪两处冲突”时，答复正确给出报价与规格书，还附带需求来源。答复聚焦度需在后续版本改进。
- 当前 CLI 读取可信开发样例和 PDF 解析缓存；没有正式上传 API、真实采购资料验收、MySQL 会话持久化或 Linux worker 业务任务。
- 只完成内存字段的最小业务链路。其他七个字段、三家供应商全面审查、复杂表格/忽略区域的完整覆盖、深入模式和独立验收集留待后续阶段。
- 状态准确率、证据定位率、危险误判率、延迟和费用均未按正式验收集测量；路线图中的目标仍是目标。
- 本地 `.env` 和 `data/` 被 Git 忽略。代码、模拟包清单、依赖记录和本小结保存到仓库；密钥与真实运行 JSON 留在本机。

M1 在上述模拟包与内存字段范围内完成验收。进入 M2 前，按分步协作约定先说明下一小步并由用户决定是否继续。任何前端设计或代码工作仍须先暂停讨论页面流程、设计规范和样式。
