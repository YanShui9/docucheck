## 目标和边界

首版面向企业内网单组织、多账号协作的采购初审演示。使用本地 OIDC 演示账号登录；API 验证令牌并按项目/Case 授权。用户从空 Case 上传需求与最多三家供应商资料，能发起 Agent 问答和八字段审查，查看每个判定的原文证据，修正有证据支持的提取事实，回看历史并导出一致的结果。正式结果始终绑定 Case 快照、Run 和证据版本。演示形态不能被描述为已经具备公网多租户生产能力；M5 继续负责独立资料质量、成本、性能及部署运维的正式验收。

## M4-A：页面和视觉草案

**推荐的主流程：** 登录与选择项目/Case → 上传并指定“采购需求/供应商报价/供应商规格”、供应商及型号 → 等待解析并查看覆盖/错误 → 在同一 Case 内提问或运行完整审查 → 按供应商 × 八字段查看结果 → 点开判定和证据，在原 PDF 页或 XLSX 工作表/单元格核对 → 对提取事实提交有原文支持的修正，查看复核状态 → 回看旧快照和导出。

**桌面布局草案：** 左侧导航放 Case、资料、历史；中间以“对话 / 核验矩阵”作为工作区；右侧可调整宽度的证据面板显示原件、页码/坐标或工作表/单元格。来源与判定同时可见，避免频繁跨页。窄屏改为分层页面与全屏证据面板；矩阵允许横向滚动并固定供应商/指标标识，不截断状态文字。

**状态和审计规则：** 界面区分上传、解析、排队、运行、待澄清、完成、部分完成、失败、已取消/中断。只有完成且绑定当前快照的结果可显示为正式判定；旧快照有显著“历史版本”标识。每个矩阵格显示状态、简短理由和可点击来源；颜色之外必须有文字/图标。修正表单只改提取事实，不编辑原件或规则结论；同一原文支持旧值和新值时保留冲突并提示人工复核。

**已选视觉方向：专业审查工作台。** 中等信息密度，浅灰白底、深蓝灰文字，蓝绿作为主要操作色，状态色克制；矩阵和证据是视觉中心。对话区以清晰文本、来源卡和运行状态为主。保留足够字号与留白，使面试演示时能看清来源和结论。

曾比较的方向：

1. **专业审查工作台（已选）**：适合演示审计轨迹与多供应商比较。
2. **文档阅读型**：更大留白和字号，强调原文阅读；复杂矩阵需要更多滚动。
3. **传统企业后台型**：高密度表格与标准侧栏，能同时看到更多行；第一次使用时更难看清主流程。

确认方向后固定字体、间距、色彩、状态徽标、表单与表格规范；保证键盘操作、可见焦点、足够对比度和加载/空/错误态。界面不展示原始模型思考文本或密钥；模型发送范围在上传/发问前明确提示。

## M4-A 时的接口差距（已在 M4-B/C/D 范围内补齐）

- `POST /cases` 已有，但工作区需要分页列出和读取授权 Case；现有子资源路由尚无身份与 Case 归属检查。
- `GET /agent-runs/{id}` 有答复/状态、`/facts` 有事实集，完整审查需要版本化的结构化 CheckResult 读取；不能从自然语言答复反解析矩阵。
- 证据接口有页码、坐标或工作表/单元格，但缺经过授权的原件预览/下载；PDF 原页与 XLSX 原单元格定位需要这个入口。
- 修正、会话消息与运行历史原有基础路由；M4-D 已增加基于同一快照结构化结果的 XLSX/JSON 导出。
- 完整代码回归需覆盖本轮未提交的 M0–M3 修复；既有 M3 验收数不能代替当前工作树的总回归。

技术参考：Vue 官方建议新项目使用 [create-vue/Vite](https://vuejs.org/guide/scaling-up/tooling.html)；PDF 原页预览可基于 [PDF.js](https://mozilla.github.io/pdf.js/getting_started/)；表格导出须防止 [公式注入](https://community.owasp.org/attacks/CSV_Injection)。最终依赖选择待界面方案确认后在 M4-B 落实。
