# M2-0：XLSX 内存分列证据修正（2026-09-26）

本步只修复内存字段在 XLSX 中由相邻“标签单元格 + 数值单元格”组成时的漏抽与错误覆盖判断；未进入 M2-1 多供应商答复引用修正。没有读取 `.env`、启动 Docker 或调用 DeepSeek。

## 已实现

- 模型抽取批次携带 XLSX 工作表和单元格坐标，明确提示可以同时引用同一行、紧邻右侧的标签与纯容量数值单元格；配对单元格进入同一抽取批次。
- 服务端仅接受同一文档、工作表、行和供应商的明确两格关系；事实保留两个原始证据 ID。另一字段的容量、内存卡、额外容量列或带“最大支持”等语义的数值列不会被拼成已装内存。
- 完整性检查要求所有可验证的分列内存来源都有对应的双引用事实；模型漏抽时保持处理未完成，不把报价缺失误判为“满足”。
- 含合并单元格的 XLSX 暂记为 `partial` 并记录合并位置；合并关系要到 M2-2 再补正式解析，当前不据此发布业务结论。

## 离线验收

在 `docucheck` Conda 环境，后端测试 **102 passed in 5.56s**；全目录 Ruff 通过，`pip check` 无依赖冲突。新增用例覆盖：`A6=已装内存、B6=16 GB` 与规格书 32 GB 得出“资料冲突”，并保留 A6/B6 双来源；模型漏抽此配对时 `complete=false`、业务状态为空；“内存卡”、虚拟内存、存储容量、同列冲突表头、同排第二容量均不被误配；常规与重定位工作表中的合并单元格均不得标记解析完整。上述测试使用本地脚本模型，不是一次新的真实 DeepSeek 验收。

本步调整 XLSX `parser_version`，使新解析快照和证据 ID 与旧缓存区分；之前保存的 M1 运行记录保留为历史记录，不作为当前快照结果复用。

## 边界与下一步

当前只支持明确、未合并的两格“内存标签 + 紧邻纯容量值”。需要列标题、多列解释、跨行或合并关系的表格保持未完成；复杂 PDF/XLSX 覆盖仍按 M2-2 处理。另一项已确认的 A/B 供应商答复来源串家问题仍在 [M2-1](m2-task-breakdown-2026-09-25.md) 范围内。
