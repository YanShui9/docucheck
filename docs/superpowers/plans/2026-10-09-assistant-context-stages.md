# 采购助手分阶段上下文修复计划

**目标：** 修复真实十项候选追加交期在请求前失败的问题，并让清单继续增长时不靠不断提高预算维持；补齐北京时间运行时输入。

**设计：** 保留现有受控 Agent、持久候选与确认权限。完整清单留在服务端，模型上下文是按阶段组装的视图。普通聊天一次请求；修改先 prepare_changes 指定目标，再仅提供完整原 schema 的 propose_changes/chat 工具及目标字段。全量清单不会被摘要替代、自动删除或自动确认。

**依据：** 真实失败请求必需上下文 16014，上限 16000，两个 attempt 均模型调用 0；历史、摘要已全部移除，修改工具定义约 8078 字节。[LangChain 上下文工程文档](https://docs.langchain.com/oss/python/langchain/context-engineering)将模型看到的临时上下文与持久状态区分，并支持动态选择可用工具。采用这一原则，不为修复更换框架或增加依赖。

## 方案比较

- 仅提高 max_prompt：短期缓解，但复杂清单继续增长会再次失败，也增加每次聊天成本，不采用。
- 仅删除历史/摘要或压缩清单：本次可选历史已为零；采购条件不能靠有损摘要改写，不采用。
- **按阶段加载工具与指标（采用）**：保留共享调用/输入/输出预算；修改多一次准备调用，普通聊天保持一次。新增分页读取目录，完整目标字段在编辑阶段加载。

## 三个实施部分

### 1. 分阶段上下文及权限边界

- [ ] 添加十项、四十项及上限附近清单的失败回归；验证新增与单项修改保留所有未动指标的 ID、规则、来源和条件。
- [ ] assistant_checklist_context.py 提供准备参数、目录分页与目标视图。初始工具移除 8KB 修改 schema，换 prepare_changes/read_checklist；初始完整基准能放下时保留，超限时显式改用有限目录，标注尚未读取项。
- [ ] read_checklist 支持有限查询及 offset/limit；循环时替换旧目录观察，不无限堆积。准备阶段指定最多四个指标及品目；编辑阶段不携带完整清单或无关工具。
- [ ] 更新/删除必须属于已准备的目标；新增仍经原 ChecklistPatch 和完整服务端 apply_changes/validate_definition 验证。单项或单批内容自身超限时给出可操作的范围提示，保留原清单，不截断条件。
- [ ] 保留 RAG 检索后的证据工具限制、正式审查的已确认版本绑定、取消/篡改/来源验证及共享预算。记录每轮输入上界与 schema 体积等纯数字审计，区分准备/编辑/证据阶段。

### 2. 运行时间与回归

- [ ] 每次 ask 从服务端时钟取得北京时间，注入可信日期/时区；旧聊天不能覆盖，单元测试覆盖 UTC 跨日。
- [ ] 补提示缺值仍为 manual；普通聊天无需反复附加泛化免责声明，正式业务结果继续受原校验约束。
- [ ] 定向、完整离线、Ruff/pip、真实 MySQL、前端回归及独立代码审查；原真实失败请求只读回放，不调用收费模型、不重试原 Run、不改原候选。

### 3. 提交与本机应用

- [ ] 代码和脱敏证据本地提交；闲置门禁后离线更新现有后台镜像及 API，核对源码、依赖、配置、任务/索引/真实清单保持。
- [ ] 记录未执行的真实模型/浏览器验收，不把离线通过等同于模型在线行为通过；提交应用记录。

## 明确边界

清单领域上限仍为 100 项，单个模型请求仍遵循原预算，不承诺无限字段或无限对话。未读取目标不能更新/删除；跨资料版本/对话不借用候选。极端长的单项仍可能要求使用既有清单编辑器或缩小批次，不能默默丢字段。日期来自本机时钟，系统时间错误需修正宿主时间。
