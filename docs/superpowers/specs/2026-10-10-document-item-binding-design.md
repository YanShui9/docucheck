# 采购资料与品目对应设计

状态：待用户确认。2026-10-10 本步只完成代码调查、方案与验收设计；未修改应用代码、数据库、前端或运行服务，未调用模型API。

## 1. 要解决的真实问题

上轮合成审查已经完成2/2批次，但数量与交期为 `item_model_unclear`。资料上传的 `model_name=苹果手机` 实际表示泛品目，清单的 `item.name=苹果手机` 与待确认的specification没有明确对应关系；数量和交期在独立表格行。直接让型号匹配品目、跨行拼成事实原文或修改已确认要求都会绕过现有证据边界。

本设计分别表达三个概念：买方采购品目、供应商具体产品型号/SKU、原文事实所在范围。适用于水果、服装、手机等既有动态指标，不新增固定八字段。

## 2. 方案比较

| 方案 | 作用与代价 |
| --- | --- |
| A：只关联整份文件到一个品目 | 开发量较小，但多产品报价仍无法可靠区分；后续需再次改范围模型 |
| B：统一的资料范围关联（推荐） | 单品可关联整份文件，多品目按XLSX矩形范围或PDF页面分别关联；初期多一个范围确认操作，可复用同一版本/审计机制 |
| C：模型自动判定对应并直接生效 | 操作较少，但错误归属会污染正式结果；不作为本次实施方案 |

选择B作为拟定基线。模型提出对应建议属于后续增强，本次由用户明确选择并确认，后端验证原文依据。聊天“确认”不替代受权限和版本约束的业务提交。

## 3. 中文交互约定

沿用现有资料侧面板和白灰/低饱和绿色样式，不另做工作台。

1. 用户可先上传资料，也可先建立审查清单。只有当前清单明确保存确认后，才允许确认资料对应关系。
2. 资料卡片增加“关联采购品目”入口，选择已确认的品目名称；未关联显示“尚未确认对应品目”。
3. 提供“整份文件为单一品目”和“仅指定范围”两个范围选项。整份文件关联要求用户明确确认该文件只描述此品目；已发现其他品目或相矛盾的产品描述时，不允许依此消除冲突，须划分范围或保留待核对。XLSX选择工作表及矩形行列范围；PDF选择连续页面。无法精确划分的复杂表格保持未关联，需要拆分资料或后续细化。服务器的结构和原文校验不代表已自动证明整份文件语义上只有一个品目。
4. 展示可定位的品目原文作为对应依据，例如报价B3的“苹果手机”，同时预览所选范围。锚点可以在数值行之外，但必须来自同一当前文档；不得把锚点混入数值quote伪装成连续原文。锚点仅说明对应依据，不扩大可抽取范围；多个不重叠范围可以引用同一真实品目标题，但不同品目的数值范围不得重叠。
5. 将新增型号输入明确标注为“供应商具体型号／SKU（选填）”。旧“产品标识”保留原始值，要求用户明确分类为品目名称、具体型号或暂不确定，不自动把历史泛品目名称当SKU。确认是品目名称时必须匹配选择的品目和原文依据；具体型号必须有原文支持，未知仍保守处理。
6. 点击“确认资料对应关系”保存独立的对应版本。界面提示原有审查结果保留为历史，需用户重新发起审查；不自动调用模型。

第一版不自动识别名称别名；锚点须明确支持品目名，或支持已在买方规格中明确列出的具体型号。通用同义词映射、共同商务条款分配到多个品目、同页混合PDF表格精确选区暂不支持。

## 4. 数据、版本与权限

使用MySQL保存独立的不可变对应版本和当前head，复用现有Repository、幂等键、Case优先加锁、成员权限及审计约定；需要Alembic迁移。新记录覆盖以下信息：

- 对应版本ID、Case/快照、已确认清单版本及摘要、前置对应revision、操作者、确认理由与UTC时间。
- 每条对应的document_id、source_sha256、parser_version、item_id、范围选择器、服务端展开后的证据ID集合、锚点引用/原文摘要和明确的旧标识分类/可验证具体型号。
- 整个版本的canonical digest。集合数量受现有20品目、7文件、25,000证据块及API请求限额约束；范围由服务器展开，不接收任意路径、SQL或URL。

只允许当前任务editor/owner明确确认，viewer只读；买方文件角色和供应商归属不由对应请求改变。不存在、跨Case/快照/文档的ID、无原文锚点、越界/空范围、互相重叠的不同品目关联、变化后的hash/清单，以及重复请求内容不一致均拒绝。删除Case时清理新表；历史版本读取继续受成员和删除状态检查。

修改对应关系不改原件、解析记录、原文证据ID或资料revision，不触发重新解析/Embedding，也不重写买方清单。新上传造成快照变化、或重新确认清单造成版本变化时，旧对应不可直接作为当前依据；可只读预填建议，须在新上下文重新确认。

当前Case存在queued/running任务时拒绝修改对应，避免边运行边换归属；等待人工或已结束任务保持原绑定。并发提交只有一个expected revision获胜，幂等重放不增加版本。确认/取消及审查retry行为不能迁移旧attempt的归属；绑定变化后创建新Run，旧Run继续按冻结版本读取。

## 5. Agent与确定性判定

新Run固定记录 `binding_version_id` 和 `binding_digest`，由服务端读取当前合法版本，模型不能填写或覆盖。每批抽取只暴露当前品目、允许的原文范围和少量锚点说明，完整对应表留在服务端；禁止把所有对应说明重复加入每轮聊天上下文。

计划增加 `dynamic-rules-v4`，其批次ID、input_digest、报告重放、缓存复用、人工修正与任务记忆均包括绑定版本。v1/v2/v3仍走原有语义，不在旧 `Document/ScopedEvidence` 默认dump里新增会改变历史source_digest的字段；不能读取最新对应来重新解释旧报告。空绑定也有明确的冻结身份，不与其他绑定缓存混用。

v4候选事实必须满足：

1. 原文数值/单位/限定语及同一行或段落关系通过现有验证。
2. 每个事实引用处于同一个当前品目对应范围，并且供应商、解析版本和原件hash一致。
3. 原文锚点支持所选品目；明确不同品目、不同型号、条件不一致或模糊对应不因人工点击而被抹除。

品目关联负责说明“这段资料审查哪个品目”，不是数值或达标证据。事实的quote仍只引用数值原文；报告另外列出对应版本、锚点与确认记录，不把人工对应伪装成供应商承诺。

已明确品目但买方没有要求具体SKU时，可判数量等有限指标，机型仍需人工确认；已明确SKU而供应商具体型号不同，则保留现有不适用/人工守卫，不能凭品目同名覆盖型号冲突。

正式审查仍全量覆盖适用资料，解析partial/漏抽不能被范围关联升级成完整。v4记录按供应商/品目的范围覆盖与未解析、未关联或冲突情况；来源归属仍不清时保持待人工确认或处理未完成，不将范围未确认误报为“证据不足”。不将top-k无命中用于证明字段缺失。

## 6. RAG与已有Milvus索引

绑定真值保存在MySQL，不写入Embedding文本，不改变原件向量含义。普通资料浏览可读当前授权Case原文；明确指定品目的检索、取证、正式抽取及后续事实校验采用同一冻结的允许范围。

现有Milvus `SearchScope`只限制项目、Case、快照、文档、供应商及generation，不能靠文档级过滤保证同表不同品目隔离。范围检索需在已有字段上增加授权chunk_id过滤，按有限批次构建表达式，并验证返回chunk的底层证据全部在允许范围内；跨范围chunk不能直接显示。BM25与read_source使用相同范围，不能密集检索过滤后又由词法候选绕过。

不为品目绑定新增集合或强制重做所有向量。现有chunk无法精确表达范围、过滤超过预算或向量服务失败时，显式返回范围内词法降级及诊断，不称hybrid成功；没有命中不改变正式覆盖状态。锚点通过单独的受控对应详情读取，不让数值读取工具自由跨范围。

### B：中文资料对应操作

## 8. 官方参考与使用边界

- [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)：官方说明人工输入、持久化状态、恢复可能重执行节点；据此保留服务端确认和幂等写入。当前项目采用MySQL业务状态及显式新attempt，不因本功能宣称已有持久化图精确续跑，也不升级框架。
- [Milvus filtered search](https://milvus.io/docs/filtered-search.md)：官方说明向量搜索的元数据过滤；本设计采用已有scope加范围过滤，MySQL原文核验仍是最终守卫。

上述参考用于确认人工介入、幂等和检索过滤的工程模式；具体品目绑定与范围约束为基于本仓库实际失败提出的设计，不是官方采购方案或已实现能力。
