# DocuCheck 阶段 0：环境与固定样例设计

## 目标

在开始业务功能前，建立可复现的开发基线，并用一套完全模拟的文档证明 PDF/XLSX 的原件位置可核对。阶段 0 的产物不是准确率或性能验收结果。

## 范围

- 本地 Git 仓库、精简 README、Python 3.12 独立环境记录。
- 一份需求 PDF、一份同型号报价 XLSX、一份规格 PDF；文件均由本项目构造，不含真实采购资料。
- 每个「供应商 × 字段」一条标准答案，包含状态、需求与供应商的原件定位、原始文本及判定理由。
- Docker Desktop、E 盘挂载、MySQL/Redis/Linux worker 和 MinerU Basic 的可行性检查记录。现存 Docker 数据盘与配置须先查明状态；不得通过重置或清空数据来排除故障。

## 样例设计

需求统一写明：内存至少 16 GB、标称存储至少 512 GB、屏幕至少 14 英寸、主机重量不超过 1.6 kg、质保至少 24 个月、数量 10 台、含税单价不超过 6000 元/台、订单确认后 14 个自然日内交付。

供应商 A 报价单标注型号 DC-14-A，写明已装内存 16 GB、数量 10 台、含税单价 5800 元/台、合同签订后 10 个工作日交付。规格书标注同一型号，写明已装内存 32 GB、标称 SSD 1 TB、屏幕 14 英寸、主机重量 1.8 kg。两份供应商材料均不写质保。

预期八字段状态：内存=资料冲突；存储=满足；屏幕=满足；重量=不满足；质保=证据不足；数量=满足；单价=满足；交期=待人工确认。交期的起算事件和日历口径均不一致，不进行猜测换算。需求与供应商证据均要记录 PDF 页码或 XLSX 工作表/单元格；缺失质保需记录两份供应商文件已成功处理的前提。

## 模块边界

- `examples/dev-pack-001/` 保存模拟原件和标注清单，供人工检查及后续解析测试。
- `docs/development-roadmap.md` 记录阶段目标和完成情况。
- `docs/environment/` 保存可复现命令、版本和故障证据；不得写入密钥或真实采购内容。
- 后续解析器只消费文件和角色/归属元数据；标准答案不得注入运行时判定链。

## 验证与退出条件

1. 项目 Python 环境实际输出 3.12.x，README 可解释如何激活。
2. 三份原件能人工打开；PDF 可提取文本且页码明确，XLSX 的单元格定位稳定；八条标注逐条对应原文。
3. Docker 侧只有 Linux Engine 可连接、E 盘挂载读写、基础服务健康检查和 worker 可启动后，才把容器链路标为通过。失败需保留命令、错误和影响。
4. MinerU Basic 至少在这一套开发样例上记录版本、配置、原文/页码质量和耗时；该结果不替代独立验收。

## 风险

当前 Docker Desktop 4.91.0 在初始化 Ingest server 时无法重命名旧 `sailor-ingest.sock`，且启动日志记录了恢复出厂设置操作。需核对已有容器数据状态后再做修复。Python 3.12 环境与样例生成可独立推进。
