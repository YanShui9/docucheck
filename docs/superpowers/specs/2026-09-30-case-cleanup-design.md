# M3-12b：Case 受控清理设计

日期：2026-09-30。承接 M3-12a 的删除请求栅栏。范围是可重试地清理一个已请求删除的 Case 的数据库内容与上传原件；保留最小 Case 墓碑用于查询删除结果。本步不调用模型，也不涉及前端。

## 方案

采用数据库租约、持久文件清单和分段清理。数据库事务与文件系统删除无法原子提交，因此先在 Case 行锁下记录各 `storage_key`，再移除该 Case 的文档引用；逐文件确认其他 Case 没有引用后删除本地受管文件，并在清单中记下处理结果。最终在单一事务中按外键顺序删除 Run、事件、审计、快照和供应商等记录，设置 `deletion_completed_at`。文件不存在视为重试后的已删除状态。

Case 标记删除后不得再产生新写入；清理开始后证据、事实和文档读取也停止。运行中 Agent 和解析任务已在 M3-12a 被取消并提高 fence，迟到结果不得重新写回。已完成删除的 Case 只提供删除状态，不再提供原资料或问答记录。

## 约束

- 只接受服务端生成的 `uploads/<两位十六进制>/<32 位十六进制>.(pdf|xlsx)` 相对键，并验证目标仍在受管上传目录下；路径穿越或符号链接一律拒绝。
- 一个物理文件可能由同一 Case 多个快照或不同 Case 引用。清单每个键只记录一次；其他 Case 仍引用时保留文件。最后一个引用 Case 清理时删除文件。
- 多清理进程通过 Case 行锁、`SKIP LOCKED` 和租约竞争；过期或已被接管的 claim 不能更新数据库。大文件或缓慢文件系统操作不能让旧 claim 在过期后继续提交。
- 文件删除失败应保存可见错误并允许重试；清理器重启后可从清单继续。清理前的 Case、Run 和证据在失败时不应被错误地标为 `deleted`。
- 实验只使用测试创建的合成 Case 和临时文件。迁移和测试可执行；启动长驻 cleaner 前必须确认其会处理哪些真实待删除 Case。

## 验收

SQLite 离线测试覆盖多快照、跨 Case 共享文件、重试、租约过期、路径逃逸、迟到任务栅栏及 API 状态。MySQL 定向测试用合成 Case 和临时文件验证外键删除顺序及共享原件。检查 Alembic 升降和元数据一致性，运行后端全套测试、Ruff 和依赖检查。
