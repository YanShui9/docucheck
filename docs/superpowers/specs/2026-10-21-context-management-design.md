## 1. 目标和范围

不同采购任务分别选择自己的上下文；每次调用按照所用模型的容量组织信息。接近阈值时，整理旧工具结果和较早对话；仍放不下时缩小资料批次，保留进度继续处理。用户能够查看当前请求的占用与历史整理状态。

本轮只讨论窗口容量、历史保留与压缩、超限恢复、有限长期记忆以及用量查看。资料关联、历史资料加载、回答排版等其他问题不纳入本稿。

继续使用现有 Python、LangChain/LangGraph、MySQL 和 Vue 后端与前端。不为上下文管理更换 Agent 框架，不新增多 Agent、通用记忆平台或另一套向量数据库。前端位置、样式和主要交互在实施前单独确认。

### 2.1 两种额度的通俗解释

- 单次窗口：模型这一次能看到多少内容，输入和输出共同占用。每次调用重新计算；不是整个采购任务的存储容量。
- 任务累计用量：完成这次用户请求期间，所有模型调用实际用掉多少。这里指一次请求的执行过程（Run），不是一个采购任务从创建到结束的全部对话。相同历史重复发送也会重复计入，和窗口占用分别统计。
- 16,000/48,000 是当前应用限制，不是 DeepSeek 的模型规格；两者现有预留/校正口径也不能直接当作精确 token 百分比。

举例仅说明累计的含义：四次调用各用约 15,000 token，单次都小于 1M，但累计约 60,000 token。固定 48,000 的任务限额可能先停止任务。这个例子没有把现有 16,000 字节估算值当成 15,000 token。

另一个更直接的例子：同一份约 10,000 token 的资料发给模型五次，每次窗口里仍只有这一份资料和各次问题，累计输入却约为 50,000 token，不能据此判断当前窗口已经装了 50,000 token。当前代码还会在每次调用前按保守估算预留额度，因此可能比这个简化例子更早停止。

## 4. 信息分层与版本

| 层级 | 管理内容 | 延续范围 |
| --- | --- | --- |
| 账号 | 用户明确确认的有限偏好 | 同一身份；每次检查删除、过期和版本 |
| 工作区 | 任务归属和访问权限 | 本期不自动沉淀通用采购事实 |
| 采购任务 | 任务目标、未完成事项、当前权威记录的位置 | 同任务的不同会话可按权限读取 |
| 对话 | 近期原话、较早历史摘要、原消息引用 | 对话内维护自己的近期历史和摘要 |
| 资料/清单版本 | 文件原文、确认规则、审查结论 | 绑定明确的资料快照及清单版本 |

同一任务新建对话，读取任务概况和当前已确认记录，不自动合并其他对话的未保存候选。不同任务的采购事实不互相带入；账号偏好可按明确保存的范围共享。

资料升级后，旧聊天和旧报告保留。新请求读取当前目标版本；需要延续的任务目标、待办与版本变化说明经过来源/版本校验后进入上下文。旧报价和旧结论不能凭摘要成为新版事实。当前没有这套完整的跨会话/跨版本交接机制，需在后续独立步骤实现。

## 5. 容量与累计用量策略

### 5.1 单次窗口

以模型配置及对应接口可用能力为依据。每次按最终发送的消息、工具定义、工具结果、当前问题、格式/语义修复说明计量；每次修复都是新请求，重新计算。

优先使用已核实与模型匹配的分词方式；无法可靠计 token 时明确记录估算方法和单位，不能用 OpenAI 其他模型分词器冒充 DeepSeek 的精确分词。接口返回的 usage 是本次调用的已知实际用量，不是下一次请求的精确大小。

以下参数中，输出预留和5%安全空间已在A2a完成源码及离线验收；整理阈值仍待后续实施：

- 预留当前阶段的输出额度，再预留模型窗口 5% 的安全空间，得到可用输入额度。
- 当前输入达到可用输入额度 75% 时尝试整理，整理目标为可用输入额度 50% 以下。
- 比例可配置；要求 `0 < target < trigger < 1`，预留之后仍有正输入容量。
- 75%/50%/5% 是本稿提出的初始值，不是模型官方要求或已经验证的最佳值。验收使用小窗口模拟边界，不靠重复真实 1M 请求试错。

只有可靠计量后才能使用对应 token 阈值。当前A2a沿用A1的 legacy 字节估算并注明准入方法，不计算伪精确 token 百分比。

### 5.2 整次任务用量

A2a已实现累计输入和累计输出默认只统计，不再以固定 48,000/6,000 等数值默默截断长任务；用量预警待后续。原每次输出上限、调用次数、工具次数、耗时和取消机制仍分别限制执行；后续摘要调用也必须计入用量和调用次数。

如果用户或维护者明确设置总 token/费用硬限，配置应单独可见，超限说明这是任务用量限制，不能显示成窗口已满。没有明确硬限时，不因为累计已经超过一个窗口就结束采购任务。

启用新策略时需检查所有使用 `max_input/max_output` 的路径，不能只移除 `max_prompt=16000`，也不能通过更换错误码掩盖另一处固定额度。未知 usage 不记为 0，不盲目重发未知结果的请求。

## 6. 自动整理、回读与恢复

每次调用前执行：完整请求计量 → 选择相关信息 → 判断阈值 → 必要时整理 → 再计量 → 调用模型。

整理顺序：

1. 移除重复且可回读的旧工具观察；保留正在使用的证据、版本与回查位置。成对保留工具调用及结果，不能制造非法消息序列。
2. 将较早完整问答整理为摘要，优先保留近期原话、当前完整问题和待澄清回复。摘要只记录目标、决定、未决事项、下一步和原记录位置。
3. 摘要调用自身也必须放得下；按有界历史分组，不把整段超限历史原样重新发送。模型摘要经结构、范围与来源引用校验后，才保存新版本。
4. 仍超限则缩小本次原文或指标批次。正式审查维护完整覆盖计划，不能把被分出去的内容当成“已查完”或“没有证据”。

同一逻辑请求最多 3 次上下文重组，其中模型摘要最多 1 次；有实际缩减才继续。后续批次继续受原任务调用/耗时保护。单个不可分规则或当前问题本身过大时，保留已完成进度并明确提示如何缩小范围；不截断规则条件或原问题。

原始对话和业务记录不因压缩删除。摘要只作为辅助上下文，不作为采购数值或正式审查结论的证据。资料或权限变化时拒绝旧摘要覆盖权威记录；摘要生成失败时不覆盖上一版有效记录。

## 7. 有限长期记忆

继续沿用 MySQL 保存原对话和已确认个人偏好。在后续记忆步骤新增版本化的对话语义摘要、同任务的概况/待办，并保留来源消息、资料/清单版本、生成时间和来源摘要。

持久化提交沿用 Case/Run 的权限、版本、attempt/fence 校验；并发生成不能用旧摘要覆盖新状态。删除任务或撤销访问后，不能通过账号偏好或任务摘要继续获取原业务内容。

一期不自动学习跨任务价格、供应商信誉等通用事实，不增加任意个人事实记忆。是否保存新的偏好仍要求用户明确确认。

## 8. 用量展示的待确认范围

拟提供小型入口，展开显示本次请求占用、可用上限、剩余空间、是否整理过历史，并区分对话、规则、资料、系统/工具说明、预留输出。累计调用量和费用另列。

有匹配计量显示 token；估算显示“估算”；旧记录缺少计量显示“未记录”。不把累计费用统计显示为窗口已用比例，也不显示未经测量的精确来源占比。

前端入口位置、触发方式、样式和无历史数据状态仍需与用户确认。本次只确定后台需要提供的数据含义，不创建组件或页面。

## 10. 最终验收例子

- 苹果任务接近阈值时整理历史，服装任务不受影响；两者各次请求遵循所用模型窗口。
- 同任务新对话能够获取目标、待办和当前确认规则位置；其他会话未确认的提议不自动生效。
- v1 单价上限 25、v2 改为 23 后，当前回答读取 v2 的确认记录；历史报告仍可按 v1 回看。
- 多次调用累计超过 48,000，单次均合法且没有显式任务硬限时，不因旧固定额度停止。
- 历史和工具结果触发整理后继续；单个大原文触发分批；格式修复额外信息同样计量。
- 所有上下文拒绝都有数字诊断；没有实际调用则不记模型消耗；未知 usage 保持未知。
- 取消、权限变化、来源变化、旧 attempt 迟到、摘要失败均不覆盖当前业务记录。
- 用量窗口不混淆本次占用和累计消耗；计量不足时明确标注估算或未记录。
