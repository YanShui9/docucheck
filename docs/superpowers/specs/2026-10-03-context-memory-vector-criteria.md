## 1. 用户要求及现状

用户要求设计上下文、保存记忆、向量库与向量检索，允许手动设置审查指标，或者从需求、订单识别指标，并说明时间成本。

| 机制 | 当前实际代码 | 本次扩展 |
| --- | --- | --- |
| 上下文 | context.py 读取最近四轮、焦点和待澄清项，限制输入 token；工具观察有压缩 | 按意图和权限装配，近期窗口 + 可追溯摘要 + 按需历史读取 |
| 保存记忆 | MySQL conversations/messages、agent_runs.memory_json；session_memory.py 验证资料指纹、事实/结果范围 | 独立的会话摘要、版本化任务状态、用户明确保存的偏好及模板 |
| 检索 | retrieval.py 使用 BM25Plus，按快照/供应商过滤并保留来源定位 | Milvus 向量 + BM25Plus，排名融合、原文回读和检索评测；Attu 管理与调试 |
| 指标 | FieldKey 八项枚举，数值事实及对应规则，工具数组上限八项 | 有稳定 ID、有限规则类型、来源与版本的动态清单 |

完整消息保存与模型本轮看到的上下文是两件事。持久化允许重启后恢复；上下文装配决定这次调用应该读取什么、占用多少 token。

## 2. 技术方案比较与推荐

| 方案 | 收益 | 成本与适用条件 |
| --- | --- | --- |
| **MySQL + Milvus Standalone + BM25Plus（用户指定 Milvus，推荐此部署方式）** | 保留现有关系数据和权限实现，引入向量索引；已有 Attu 可观察集合、索引和查询 | 需要检查本机资源、官方配套部署、SDK/Attu 兼容及跨库失败恢复 |
| PostgreSQL + pgvector | 若关系数据本来在 PostgreSQL，可在同一数据库维护向量与业务数据 | pgvector 面向 PostgreSQL；本项目已经使用 MySQL，选择它会增加 PostgreSQL 或涉及数据库迁移 |
| 继续仅用 BM25Plus | 现有实现可直接复用，运营成本较低 | 尚未实现用户此次要求的向量检索；只保留为对照基线和受控降级路径 |

Milvus 提供标量过滤、多向量混合查询及不同部署形态。首版使用 Standalone、应用层 BM25Plus + 稠密向量融合；暂不要求把词法检索迁入 Milvus。已有中文分词、别名及表格分组作为对照保留，迁移内置 BM25/分析器需单独证明质量和性能收益。[Milvus 部署方式](https://milvus.io/docs/install-overview.md)、[标量过滤](https://milvus.io/docs/boolean.md)、[混合查询](https://milvus.io/docs/multi-vector-search.md)、[pgvector 官方仓库](https://github.com/pgvector/pgvector)。

Attu 通过服务端地址和凭据管理 Milvus；应用直接使用 pymilvus 适配层访问，不依赖 Attu 是否打开。本机已安装 Attu 2.6.4，旧 Milvus 容器全部退出，连接尚未验证。优先评估官方单容器嵌入式 Standalone，资源及版本核对后才选定配套安装文件；不直接覆盖旧容器和数据卷。[Attu 2.6.4 官方说明](https://github.com/zilliztech/attu/tree/v2.6.4)、[Milvus 2.6 Windows 部署](https://milvus.io/docs/v2.6.x/install_standalone-windows.md)。

聊天模型继续通过现有 Provider 适配层调用。Embedding 单独配置 Provider、模型 ID、模型修订、维度、超时及批量上限；推荐先以本地 BGE-M3 作为可复现基线。其官方模型卡标注多语言、1024 维及最大 8192 token；本设计仍采用较小的业务分块，不以最大长度作为默认分块大小。CPU/GPU 速度与中文采购召回尚未实测。[BGE-M3 官方模型卡](https://huggingface.co/BAAI/bge-m3)。

本地 Embedding 会占用模型下载、磁盘、内存和计算资源；云端方案可降低本地推理负担，但需要独立 API 配置、数据发送说明及费用核对。现有 DeepSeek 聊天配置不作为 Embedding 接口可用的证明。实施前探针验证维度、有限数值、批量响应及超时，固定模型修订和依赖版本。

## 3. 组件职责与数据流

| 组件 | 职责 | 权威数据/依赖 |
| --- | --- | --- |
| ConversationService / MemoryRepository | 保存消息、摘要、任务状态及用户确认记忆；处理版本与删除 | MySQL、当前 OIDC 身份及项目权限 |
| ContextAssembler | 根据意图、预算和版本构造本轮上下文，记录选择/省略原因 | 上述仓库、已确认清单、证据与结果服务 |
| EmbeddingProvider / IndexWorker | 分块向量化、幂等入库、重试、重建 | 已解析原文、索引任务、Milvus |
| EvidenceRetriever | 服务端范围过滤、BM25/向量召回、融合、原文回读 | MySQL 授权/资料清单、BM25Plus、Milvus |
| CriteriaService | 草稿、来源校验、用户确认、版本化和模板 | 原文或明确用户要求、有限规则 schema |
| RuleEvaluator | 对同品目/口径的有效事实执行确定性规则，形成可解释结果 | 清单版本、验证事实、规则版本、覆盖记录 |
| LangGraph Agent | 普通答复、动态检索/读原文、澄清与提出审查范围；正式审查调用受控批处理子图 | 有类型的状态/任务简要计划、上述服务、预算及批次进度 |

新资料的数据流：上传 → 确认业务角色 → 解析并保存原文 → 写入索引任务 → 批量向量化 → Milvus 入库 → 强一致读取核对内容/索引并确认可检索 → 标为就绪。

问答的数据流：鉴权 → 读取当前会话/任务版本 → 判断意图 → 按需检索或读取历史 → 装配上下文 → 模型/受控工具 → 保存真实答复与已确认变更 → 后台更新摘要。

正式审查的数据流：已确认清单 + 适用资料 → 按品目、供应商、指标批量抽取 → 校验每条事实来源和处理覆盖 → 规则判定 → 绑定版本的结果与报告。语义召回用于寻找线索，完整覆盖由适用资料清单和抽取记录证明。

## 4. 上下文机制

### 4.1 每轮装配顺序

1. **身份与范围**：服务端读取 OIDC principal_key、项目权限及会话可见性。模型不能指定当前用户身份或放宽权限。未关联任务的普通聊天不注入任务资料。
2. **不可省略信息**：系统与工具约束、本次用户问题、当前路由、任务/资料/清单/记忆版本，明确的品目/供应商焦点和待确认事项。
3. **结构化记忆**：与本意图有关的已确认任务状态、小型个人偏好；相互矛盾的候选信息保留待确认状态。
4. **对话辅助**：有覆盖边界的摘要和最近消息；默认最多八轮，同时受 token 预算限制。被摘要覆盖的旧消息不再重复全文注入。
5. **业务内容**：检索出的原文和按需读取的验证结果。保留 evidence_ref、文档版本及定位；普通聊天不预加载所有文件。
6. **执行观察**：当前工具请求/响应按成对关系保留，较早的大响应转为可重新读取的服务端 handle。

用户问“这家交期为什么不行”时，先从当前焦点识别供应商和指标，再按本次资料及清单版本读取交期结果与原文。指代有两个可能对象时澄清，不能猜一个对象并给正式结论。

### 4.2 Token 预算和长对话

拟定首版单次输入预算为 16,000 token，可配置；输出按路径预留，普通聊天与完整报告可使用不同上限。实际允许输入取“项目输入预算”和“已验证 Provider 上下文容量减输出预留/工具开销”的较小值。配置的超大上下文数字不直接扩大每次请求。

现有 policy.py 的 input_bound 使用序列化 UTF-8 字节数进行保守预留，Provider 实际 token 用量另行记录。实施时区分预算估计与真实 token，避免把当前 16,000 的保守估计上限描述为精确发送了 16,000 token；新参数需通过实际 usage 校准。

预算分配先保留不可省略信息，再给任务状态、摘要、最近消息、检索原文分配剩余空间。摘要拟定上限 1,500 token；历史正文初始预算约 3,000，资料正文约 5,000，可根据意图重新分配。这些是实施初值，不是已测的最佳参数。

接近预算时，依次去掉不相关结果、重复/低排名片段、已摘要的较早消息及较早工具全文；需要的原文保留定位以便再次读取。不得截掉单位、比较符、金额口径或引用所需的原句。当前问题及必要工具 schema 本身放不下时，明确请求分批或附件输入，并保留用户原消息。

未摘要的较早历史达到阈值后，在后台更新摘要，保留最近消息。首次没有可用摘要时使用预算内窗口并标记历史范围；用户明确追问旧内容时先读取相应原消息，不假装已经读过全部历史。摘要失败不删除原消息，也不阻塞已经能在预算内完成的普通答复。

摘要包括采购目的、当前话题、用户明确决定、尚未解决的问题及关联 message_id；不能把猜测写成已确认事实，也不保存模型内部思维链。资料更新后，摘要中的旧业务数值只可作为带日期/版本的历史话题，当前判定重新读取原文与结果。

### 4.3 可审计的上下文

每个运行绑定 message_sequence、资料/清单/任务记忆版本及输入指纹；保存所用 message_id、summary_id、memory_id、evidence_ref、token 用量和省略原因。日志与检索诊断受原任务权限保护，不对其他账号暴露原文。

原文和记忆内容按数据处理；里面的“忽略约束”“读取其他任务”等文字不能改变系统约束或工具权限。上下文装配后仍需每次工具执行重新验证资源访问与业务版本。

## 5. 记忆保存机制

### 5.1 保存哪些信息

| 类型 | 存储与范围 | 写入/读取规则 |
| --- | --- | --- |
| 完整会话 | MySQL messages，单调消息序号；会话默认私有，也可明确共享至项目 | 用户消息接受后即保存；真实助手答复与状态保存，失败记录保留为失败；不把未完成流当完整答案 |
| 对话摘要 | 拟新增 conversation_summaries，含覆盖序号、来源消息、版本及生成模型 | 后台生成，按同会话和可见性读取；覆盖进度只能前进，引用的消息失效后重建 |
| 任务记忆 | 拟新增 task_memory，任务/品目、确认目标、待确认事项、当前清单引用 | 用户确认的变更及有效工具结果更新，按任务权限读取；资料相关部分受资料版本限制 |
| 个人偏好 | 拟新增 memory_records，按 principal_key 隔离，含类型、值、来源、版本、状态/到期时间 | 用户明确说“记住……”或确认候选后保存；支持查看、修改、删除；小型条目按键从 MySQL 加载 |
| 复用模板 | 版本化 checklist_templates，个人或明确项目共享 | 用户主动保存，使用时生成当前任务草稿；仍需确认阈值和适用范围 |
| 验证事实/结果 | 现有事实、结果及运行存储，绑定资料/清单/规则版本 | 只有来源、范围和覆盖校验通过后才进入业务判定；不能用个人偏好或摘要替代 |

例如，“回答简短一点”可以记为个人偏好；“这次采购 100 袋”保存为这个任务的要求；“甲供应商交期达标”保存在某份资料、清单和规则版本的结果里。下次采购不会因为这个旧结果自动判甲供应商达标。

首版向量库覆盖采购原文。小型结构化偏好和任务记忆由 MySQL 按范围加载；旧会话回忆由同会话摘要索引、消息序号/全文读取实现。后续若评测证明大量历史记忆需要语义召回，可建立单独的记忆集合；它必须有会话可见性和记忆状态过滤，并保持与采购证据分离。

### 5.2 一致性、删除与恢复

- 记忆变更带来源消息/操作、schema_version、expected_revision、时间和确认者。任务与个人条目分别更新，模型提出的候选不能直接覆盖已确认条目。
- 同一轮的有效状态更新与答复提交使用 MySQL 事务；需要当前 active_attempt_id/fence 和版本匹配。过期 worker、重复提交和迟到摘要不得覆盖更新后的内容。索引工作通过持久化任务在事务后完成。
- 失败运行只保存失败状态、用户输入、必要焦点和待处理项；未验证候选及未完整覆盖的结果不能升级为正式记忆。取消和重试保留原有栅栏语义。
- 删除/忘记条目先在 MySQL 标记无效并使缓存失效，再清理派生摘要/将来可能的记忆索引；记录来源抑制，后台不能重新从同一旧消息生成该条目。模型上下文不会再次注入删除条目及其摘要派生内容。
- “删除保存的偏好”和“删除原聊天”分别提供明确操作；原消息仍存在时，展示历史不等于恢复该偏好。删除消息需要使引用它的摘要失效，删除任务需要同时阻断原文、结果与索引的在线读取。
- 新资料使绑定旧版本的事实记忆退出当前判定；新清单使旧结果成为历史记录。旧报告保持原版本，不回写为新结论。
- Redis 只缓存有权限/版本/期限的读取结果。Redis 重启或过期不导致用户记忆丢失；服务重启从 MySQL 恢复。

普通聊天需要显式会话所有者/可见性及无任务会话入口。拟扩展 conversations 的归属/可见性与可选任务关联，并增加通用 chat_turns 记录；审查路径继续创建受既有外键约束的 agent_runs，不生成假的资料快照。旧项目会话按原项目权限迁移，不能随意给历史数据捏造个人所有者。

LangGraph 的运行 State 与持久化业务记忆通过仓库接口衔接；当前 memory_json 不等同已经接入 LangGraph 官方 checkpointer。官方区分会话内短期状态与跨会话记忆，并支持数据库持久化及摘要管理。本轮先复用 MySQL 业务恢复、幂等与栅栏机制；任意节点逐步检查点恢复属于另行验证的能力，不能因保存了会话就声称已实现。[LangGraph 记忆概念](https://docs.langchain.com/oss/python/concepts/memory)、[持久化及摘要示例](https://docs.langchain.com/oss/python/langgraph/add-memory)。

## 6. 向量库与检索机制

### 6.1 集合、分块与索引任务

- 集合按 embedding 模型修订、维度和分块 schema 隔离，使用版本化集合名和应用索引注册表；同集合不能混入不同模型产生的向量。
- 明确 Milvus collection schema：chunk_id 为稳定 VARCHAR 主键，embedding 为固定维度 FLOAT_VECTOR；项目/任务/快照/供应商等常用过滤项为标量字段，item_ids、evidence_refs 等结构信息使用有约束的 ARRAY/JSON 字段。小规模先用 FLAT/COSINE 做准确率基线，是否切换 HNSW 由数据量、内存和对照性能决定；不默认启用向量库 GPU 索引。
- 原文分块初值约 300–600 token、文本块重叠约 60 token，待评测调整。PDF 保留页码及段落定位，表格按行连同有来源的表头/上下文组织，避免把规格名和数值拆开；不跨文档混合。
- 每块保留有序 evidence_ref/offset 映射，嵌入文本由解析原文组装，不把模型补写文字写进原文索引。由明确品目绑定确定 item_ids，尚不明确的块标为未分配；不得默默丢掉未分配资料。
- Milvus chunk_id 使用稳定的 64 字符十六进制哈希，由项目、任务、资料快照、文档/解析版本、分块、业务绑定和模型修订派生，主键字段长度至少 64 字符。缓存也包含解析/分块/模型版本，按项目权限域隔离；未变原文可复用已授权 Embedding 结果。
- 拟新增 document_index_jobs 与 index_manifests：状态为 pending/indexing/ready/failed/deleting，含预期块数、已入库数量、内容指纹、模型修订、重试及领取租约。解析状态与向量就绪状态独立。
- 解析原文与索引任务在同一 SQL 事务登记；异步 worker 批量 upsert，核对 manifest、加载/索引状态和内容指纹，以 Strong 一致性验证新数据可读/可搜后才标 ready。重复消息可幂等执行；旧租约/版本不能把新索引标为就绪。跨库失败由重试、对账和清理恢复。
- 更换模型先构建新版本集合/manifest并验证，再切换应用注册表，保留旧版本供历史读取或清理。历史原文更新不覆盖旧报告引用。

### 6.2 过滤与召回

标量及 ARRAY/JSON 元数据至少包含 project_id、case_id、snapshot_id、document_id、document_hash、parse_version、binding_version、item_ids、supplier_id、资料角色、evidence_refs、chunk_schema 和 embedding_revision。项目/任务/快照等常用过滤字段根据所选 Milvus 版本建立适用的标量索引。

服务端从 SQL 权限和适用资料清单产生允许集合，并在两路召回前过滤。供应商问答可读取该供应商资料与适用的共享买方要求；多供应商对比由明确授权的范围合并。item_ids 未确认的资料不能用于正式跨品目匹配，完整审查将其列为待归属/覆盖问题。

初始参数：BM25 和稠密向量分别取最多 20 个候选，在应用层按 RRF 排名融合（初始 k=60，作为本项目参数），按来源去重，选约 6–10 块装配到上下文。这些是可配置且需要评测的起点，不把不同量纲的原始分数直接相加。保留通道、排名、融合参数和原文引用的诊断。

过滤表达式由服务端基于类型化、已授权的 ID 集合产生，不接收用户/模型给出的原始 Milvus filter 字符串；字符串转义、数组包含及 AND/OR 范围组合有测试。融合后的命中再次通过 SQL 校验当前访问权、任务删除状态、索引版本及原文有效性，然后从权威原文仓库读回内容；Milvus 元数据不能自行证明用户有权限。外部 Embedding 请求也在授权和资料归属确定后发送。

Milvus 默认的一致性允许短时间看不到新写入数据。首版新资料问答与功能验收显式使用 Strong，等待超过时限则报告索引尚未可读，不把它判为资料缺失；后续降低一致性必须经独立跨进程读写评测。SQL 与 Milvus 的跨库最终一致性仍由任务/manifest负责，Strong 不等于跨库事务。[Milvus 一致性说明](https://milvus.io/docs/consistency.md)。

语义示例：“什么时候能送到”可对应“合同签订后 10 个工作日”；关键词有助于定位型号、数字和明确条款。是否真的改善采购问答，需要对照 BM25 与混合检索的同一套中文问题/金标准原文测试。

### 6.3 完整性、失败与生产边界

top-k 仅代表相关候选。正式“没有质保承诺”等缺失判定必须有全部适用资料的扫描/解析覆盖记录。向量命中不能直接证明满足，仍需抽取校验和规则判定。

索引未就绪或 Milvus/Embedding 不可用时，资料问答可显式降级到已解析资料的 BM25/原文读取，并告知检索范围；不能据此给出全量缺失结论。完整审查可使用已完整解析的权威资料逐份覆盖，是否完成由覆盖记录决定，不依赖向量服务是否在线。解析缺页/失败仍报告处理未完成。

权限撤回/任务删除先在 SQL 阻断在线读取，随后异步删除 Milvus entities 并对账；不能等待物理删除完成才隔离资料。更改文档或业务绑定时，旧索引不得被当作当前资料。Attu 的管理修改不能替代应用里的采购事实修改，应用仍读取 SQL 原文并校验索引 manifest。

自部署 Milvus 在实施时配置认证/RBAC、持久化卷、内部网络和备份/重建流程；查询服务和索引服务使用不同权限凭据，Attu 使用单独管理身份。对外/跨主机传输配置 TLS，凭据不交给采购网页或模型；本机端口仅映射到回环地址。单机运行不能被描述为多副本高可用。[Milvus 认证说明](https://milvus.io/docs/authenticate.md)。

## 7. 用户设置与自动识别指标

### 7.1 三种入口及确认

1. **手动**：对话“增加净含量 25 公斤/袋、数量 100 袋、含税单价不超过 120 元/袋”，或清单编辑器录入。助手规范化字段、品目与单位，展示草稿，由用户确认；缺信息才追问。
2. **自动**：上传买方需求/订单，先确认文件角色，再按品目抽取阈值、单位、条件和原文；明确订单条款可成为要求来源。模板中但文件未写的内容只能提出建议。
3. **结合**：自动生成清单 → 用户一次确认清晰条目 → 修改/新增少数条目 → 另行解决歧义与冲突。确认界面显示来源和变更摘要，支持复用命名模板。

清单状态：draft → needs_resolution（有歧义或冲突）→ confirmed → superseded。没有确认的标准不能产生正式审查结果；用户可以只确认一个明确子集开展局部审查，输出要说明未确认/未审查项，不显示全量完成。

供应商报价、说明书及订单中的供应商承诺归为待核验事实；买方下单要求归为要求。订单的类型、是否生效及在本次审查中的角色需要明确，不能仅靠“订单”文件名判断。如果要核对订单执行，可把已确认订单作为基准，收货/交付材料作为待核验对象。

### 7.2 指标契约与规则边界

| 字段组 | 内容 |
| --- | --- |
| 身份 | criterion_id、item_id、中文名称、清单版本；显示名称不作为唯一键 |
| 规则 | type、operator、expected_value/range、unit、currency、计价/包装口径、条件、日期基准、rule_version |
| 来源 | 文档 evidence_refs，或 user_defined + 确认消息/操作/作者；混合修改保留原值、新值与变更原因 |
| 状态 | 确认状态、确认者/时间、适用范围、是否支持自动判定、必审/可选及停用信息 |

数值用 Decimal 语义，包含等值、上下限及区间；金额必须有币种与计价单位。枚举只对明确映射/标准化的值判定；自由文本要求先提取和引用，不以模糊语义相似度自动判为满足。资料存在性只核对提供/出现，不证明证照真实有效。

日期/期限规则区分绝对日期、持续时间、起算事件、自然日/工作日和必要日历。日期不存在、起点不同、缺换算或剩余保质期计算条件不足时，判待确认/处理未完成；已有用户选择“核验承诺”的交期业务口径继续保留。

用户可命名任意指标；自动执行只覆盖服务端已支持的有限规则类型。超出能力的条目保留在清单中并说明需要人工判定，不由模型生成 Python/SQL 执行。活跃指标数和一次“供应商 × 品目 × 指标”规模设置可配置上限，实施时通过容量探针确定并明示；八项不再是通用业务上限。

### 7.3 冲突、版本和既有纠正规则

需求写 100 袋、后续订单写 120 袋时，显示两条来源及时间，用户确认审查应以哪个版本/要求为准，记录理由。不存在“后来上传就自动优先”的规则。同名不同品目/单位的指标不去重。

用户可以改变自己的买方要求，来源标为用户设置/确认变更。文档里没写的阈值不得伪装为原文抽取。人工纠正供应商事实继续遵守先前约定：新值需原文支持，原文同时支持旧值和新值时保留冲突及复核标记。

每次确认新清单生成不可变版本。审查结果绑定资料、品目、供应商、criterion_id、清单版本、事实/覆盖记录及规则版本。旧八字段及 fields-v4 报告保留原含义，通过兼容适配读取，不能用新规则偷偷重解释。

## 8. 时间与资源成本

### 8.1 用户操作时间

目标是“上传 → 集中确认 → 问答/审查”。用户无需逐字段先设计 schema。草稿自动识别仍需集中确认；已有命名模板可复用。多品目、需求/订单冲突、单位缺失、低质量扫描件会增加确认与等待时间。

少量、条款清楚的资料以分钟级完成清单准备作为体验方向；这不是当前实测。对没有歧义的十条指标，不设计成十轮逐一问答。若业务标准本身不明确，助手仍要提出必要问题。

### 8.2 每次运行时间与费用

- 初次上传支付解析、批量 Embedding 和指标抽取成本；相同授权范围内的未变资料复用结果。查询只生成问题向量，不重复向量化全部文件。
- 每轮优先读取 MySQL 中的结构化记忆和已有摘要；摘要按阈值后台更新，避免每次全历史总结。近期消息在摘要尚未更新时直接使用。
- 指标按同品目/资料批量提取多个候选，采用可控批次和覆盖记录；不为每个简单指标增加独立规划循环。规则比较在本地执行，只有解释/抽取等环节调用模型。
- 增加动态指标会增加抽取和核验规模；向量检索缩小问答阅读范围，完整审查依然要覆盖适用资料。两者耗时分别测量。
- 首版不默认加入昂贵重排。只有失败样本和对照试验证明质量收益、延迟可接受时加入。

总延迟分开记录：排队、解析、索引、问题 Embedding、检索、上下文装配、模型/工具和输出；冷/热资料、CPU/GPU、供应商数与指标数分开统计。已有设备五文件 62.125 秒的记录不作为这次扩展的性能承诺。

### 8.3 开发改造成本

| 工作 | 相对规模 | 主要风险 |
| --- | --- | --- |
| 上下文/记忆 | 中等 | 长对话信息丢失、并发更新、删除及权限失效 |
| Milvus/Embedding/混合检索 | 中等 | 旧实例恢复、Docker 内存、中文表格召回、写入可见性、跨库失败与重建 |
| 动态指标 | 较大 | 现有八字段贯穿抽取、规则、工具、SQL、导出与页面；需要兼容迁移 |
| 聊天页面与新业务验收 | 较大 | 操作流变更、来源可理解性、多品目真实端到端及回归 |

粗略开发估算：有现有代码基础、单人熟悉项目、资料格式暂不扩大、Embedding 模型可正常部署的情况下，上下文/记忆约 2–3 个有效工作日，向量检索约 2–3 日，动态指标及迁移约 4–6 日；后端合计约 8–12 日。页面改版及端到端验收额外约 4–6 日。这里包含实现、回归和故障验证，是工作量估算，不是交付承诺或当前完成度；CPU 推理不足、新规则及迁移问题会增加时间。下一步执行计划用实际验证校正估算。

以上为上一版的条件估算；Milvus 的资源/旧容器排障和新增审查批次持久化尚未计量。本次不把估算升级为工期承诺，先以一个小集合、一个多轮会话和一个动态审查任务测出实际用量，再调整执行计划。

保持主草案四步：设计/契约定稿 → 后端机制与动态清单 → 聊天前端 → 多品类联调验收。第二大步内部按“会话/记忆 → 检索 → 动态指标”依赖顺序实施，但不拆成几十次用户确认。每个可验证模块先离线验证，实服务阶段先提供操作/安装说明。
