# DocuCheck 单 Agent 审核设计 v0.1

日期：2026-09-24。依据用户提出的“上传资料后由用户提问，系统调用大模型”交互方向，对原有固定审核工作流作增量调整。本文件是下一阶段的实现设计；当前仓库尚无 Agent、模型 Provider、文档业务处理或问答 API。

## 用户流程

1. 用户上传一份采购需求，以及某家供应商的报价与规格书；上传时指定文件角色和供应商。系统完成文件校验、解析和证据索引，显示每份文件的处理状态。
2. 用户输入问题，例如“这家供应商是否满足需求？”、“内存为什么有冲突？”或“交期证据在哪里？”。“审核全部八项”是一个标准问题，可由按钮发起。
3. 单 Agent 根据问题选择受控工具：检索原件证据、提取候选事实、调用八字段规则核验、读取已有结果。必要时可继续选择工具，但有步骤、时间和成本上限。
4. Agent 返回中文答复，并列出所依据的 PDF 页码/原文或 XLSX 工作表/单元格。正式五类状态来自 Python 规则引擎；模型负责理解问题、选择工具、提出候选事实和组织解释。
5. 用户可以追问、查看原件、修正有来源的事实并重算。问答历史关联 Case 与输入版本；文件变更后，旧答复标记为基于旧版本，不当作当前结论。

首版问答范围限于这批文档、八个核验字段、型号关系和证据解释。超出范围的问题明确说明无法从当前资料核实，不调用网络搜索或其他外部工具。

## 架构与职责

```text
上传 PDF/XLSX → 校验与解析 → 带位置的 EvidenceBlock → MySQL
                                           ↓
用户问题 → LangGraph 单 Agent ⇄ 受控工具 ⇄ EvidenceBlock / CheckResult
                      ↓
             LangChain 模型/工具接口 → 配置化大模型 API
                      ↓
             证据验证 + Python/Decimal 规则 → 带引用的答复
```

- **LangGraph** 保存本次问答的状态、工具调用轨迹和受限循环；负责超时、中断和重试边界。
- **LangChain 模型/工具接口** 描述可调用工具及模型消息。具体 Provider 和模型 ID 通过配置选定；不把单一厂商写死在业务层。
- **解析适配器** 使用 MinerU/openpyxl 产出统一证据结构。解析是受控的服务步骤，不能由模型传任意文件路径执行。
- **候选事实抽取** 可以调用大模型，但输出必须符合 schema，并带 `evidence_refs`。服务端验证引用属于当前 Case、文件版本及解析版本，核对原文与值。
- **规则核验工具** 比较八个字段并返回五类状态、理由和证据；模型不得自行写入或覆盖状态。MySQL 保存权威结果，Redis 仅传递任务消息。
- **答复生成** 可以用模型把工具结果组织成自然语言；引用只能来自已验证证据。无证据或解析未完成时如实说明。

### 首版 Agent 工具白名单

| 工具 | 输入 | 输出与限制 |
| --- | --- | --- |
| `search_evidence` | Case ID、当前输入版本、字段/关键词 | 已索引的证据片段与来源位置；只查当前 Case |
| `extract_candidate_facts` | 当前文档证据 ID 集合、字段 | schema 化候选事实和 evidence_refs；不返回业务状态 |
| `evaluate_checks` | 当前 Case、供应商、字段集合 | 规则引擎的状态、原因及已验证证据 |
| `get_check_results` | 当前 Run、字段集合 | 已保存的不可变结果快照 |
| `get_source_excerpt` | 证据 ID | 受控原文、页码或工作表/单元格；不接收文件系统路径 |

每次问答最多四轮模型工具选择；最大调用时间和预算作为配置项，超限返回明确的未完成状态。Agent 不获得 shell、任意 SQL、网络搜索、文件写入或直接修改判定的工具。实际阈值在模型选定后按开发集测量确定。

## API 与存储增量

保留原有 `/api/v1/cases`、文件、运行、证据和导出 API。新增设计接口：`POST /api/v1/cases/{case_id}/questions` 创建一次提问，`GET /api/v1/cases/{case_id}/questions/{question_id}` 获取状态、答复、引用及工具轨迹摘要。写入时带 `expected_revision` 和 `Idempotency-Key`；长任务经 Celery 执行，前端轮询当前状态。完整工具输入与模型输出留在内部审计记录，不将密钥或无关原文写入前端响应。

问答记录包含 Case、输入版本、问题、模型 ID、提示词/Agent 版本、工具调用摘要、引用的 Evidence/Run ID、耗时和状态。回答与审核运行快照关联；文件替换或修正后新建运行，不篡改旧回答。

## 失败与验收

- 文件解析失败或未覆盖：Agent 不得据此声称“没有该字段”；正式状态不得判满足。
- 模型超时、无效工具调用或无效 evidence_refs：运行标为 failed/partial，保留可用的解析与规则结果；不能把系统错误转换成“待人工确认”等业务状态，不编造引用。
- 相同用户问题在同一输入版本上可重试，但外部模型调用可能重复计费；按 question/attempt 记录，不承诺 exactly-once。
- 首个可运行样例使用 `examples/dev-pack-001/`，输入“供应商 A 是否满足采购需求？”。运行轨迹应证明真实模型 API 被调用、Agent 根据问题选择至少一个工具，回答指出内存冲突、重量不满足、质保证据不足和交期待确认，并给出可回到原件的引用。开发与 CI 使用 Fake Provider；真实调用只发送模拟或获准资料。

## 分阶段落地

1. 阶段 1：PDF/XLSX 解析、覆盖状态、EvidenceBlock 与原件位置；只用现有模拟包。
2. 阶段 2：LangGraph 单 Agent、LangChain 模型/工具接口、Provider、五个白名单工具、事实证据校验和八字段规则；先跑通命令行/服务层问答，记录真实模型调用。
3. 阶段 3：Case/Question/Run API、MySQL 持久化、Celery 执行、幂等与版本快照。
4. 阶段 4：上传、提问、追问、证据查看、修正、历史和报告的 Vue 页面。

原有质量与性能目标继续作为验收目标；Agent 问答还需单独统计工具选择正确率、引用有效率、超时和成本。模型供应方、模型 ID 与问答预算在接入真实 API 前配置和验证。
