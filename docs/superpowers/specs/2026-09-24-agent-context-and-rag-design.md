## 1. 真实模型 Provider

Provider 是连接某个实际大模型 API 的适配器，不是模型本身。业务层只调用统一接口；适配器负责把消息和工具 schema 发给已配置的服务，解析模型的文本或工具调用，并返回模型 ID、用量、耗时和错误。至少要有 `FakeProvider`（开发和 CI）与一个真实 Provider（用模拟或获准资料验收）。

统一输入：系统约束、当前问题、经过服务端装配的证据上下文、可用工具 schema、超时与输出预算。统一输出：结构化文本或工具调用、模型 ID、token 用量、结束原因、请求标识；不接受模型自报的业务状态作为权威。真实 Provider 的服务类型、base URL、模型 ID 和密钥由本地配置选择；密钥只从环境变量读取，不进入数据库、日志、任务消息或报告。对超时、限流和 5xx 设置有限重试；对无效输出保留错误，不静默换模型。当前尚未选定实际模型或调用过 API。

## 2. 上下文机制

上下文分三层，均绑定当前 `case_id` 和输入版本：

1. **长期事实层**：MySQL 中的 Document、EvidenceBlock、解析覆盖状态、经过校验的事实、规则结果及不可变 Run 快照。文件替换后新建版本；旧版本答复可以回看，但不混入当前问题。
2. **会话层**：当前 Case 的最近问题、答复、引用和用户确认/修正。追问可引用前一轮的供应商、字段和证据 ID；不能读取其他 Case 的历史。历史变长时保存可验证的摘要和原始消息引用，摘要不替代原始证据。
3. **单次 Agent 状态**：问题、识别的意图/字段/供应商、允许访问的文档 ID、检索到的 evidence IDs、工具结果、步骤次数、耗时/用量和最终状态。LangGraph 状态保存原始结构化数据；每个节点按需生成提示词，不把整份 PDF 或全部历史长期塞进消息。

装配顺序：固定系统约束 → 当前问题及必要的最近对话 → 当前输入版本和文件覆盖状态 → 检索到的证据及来源 → 已有规则结果。模型上下文设可配置输入 token 上限，并预留输出与工具调用空间。超过预算时先缩减旧对话和低相关证据；如果关键证据放不下，返回上下文不足或分步处理，不能删掉关键证据后继续给出确定性结论。记录每次送入的 evidence IDs、上下文版本和 token 用量，以便复核。具体 token 上限在模型确定后配置。

## 3. “思考模式”：可检查的决策步骤

这里的思考模式是 Agent 的显式决策流程，不依赖或保存模型的私有思维链：

```text
理解问题 → 确认 Case/版本/供应商/字段 → 检索证据 → 选择工具
      ↑                                      ↓
      └──── 必要时继续检索 ← 校验工具输出 ← 执行受控工具
                                             ↓
                                  校验证据与规则状态 → 生成带引用答复
```

- 问“是否满足”或要求比较数值时，必须调用 `evaluate_checks`；模型不能绕过规则工具直接生成五类状态。问来源时可调用 `search_evidence` 和 `get_source_excerpt`。
- 每轮只接受白名单工具及通过 schema 校验的参数；工具输出写入结构化状态。最多四轮模型工具选择。超时、预算耗尽、工具失败或文件版本变化时终止并返回明确运行状态。
- 保存可展示的**行动摘要**：识别了什么问题、调用了哪些工具、使用了哪些 evidence IDs、规则给出什么状态、为何结束。既不要求模型输出私有思维链，也不把未经验证的模型推理作为事实。
- 若选定的模型 API 提供推理强度等参数，可在 Provider 配置中设置并记录；这是模型调用选项，不替代上述工具、证据和规则校验。
- 生成答复后做最终校验：每个引用属于当前版本，每项正式状态与规则结果一致。校验失败时返回失败或需要人工复核，不把未经验证的答复展示成确定结论。

## 4. RAG：按 Case 检索后生成

RAG 在这里指先从当前资料中检索相关证据，再让模型基于这些证据和规则结果作答；不等于必须引入独立向量数据库。首版最多七份文件，先使用本地、可复核的检索器，后续根据开发集漏召回情况决定是否加入 embedding 与重排。

**索引单位。** PDF 以 MinerU 的证据块为基础，保留相邻块、零基页码、bbox、原文和解析版本。XLSX 以单元格为基础，检索时可带同一行的字段标签/表头，但引用仍指向具体单元格。元数据含 Case、输入版本、document_id、角色、供应商、型号、字段候选和处理覆盖状态。文本与元数据都存于 MySQL；首版可以在当前 Case 的有限证据集合上内存检索。

**召回顺序。** 先按 Case/版本/供应商/角色做硬过滤，再用字段词典、中文字符片段和精确数值/单位匹配召回，按关键词覆盖、字段/型号匹配和位置邻近排序；返回有限数量的候选块及相邻上下文。工具返回 evidence IDs 与来源位置，模型不能自造新 ID。后续若独立开发集显示语义改写导致漏召回，再增加 embedding/hybrid 检索，并比较证据定位率和成本。

**关键区别。** 定向问答可使用排序后的少量证据；“审核全部八项”与“证据不足/资料冲突”不能仅凭 top-k 检索结果下结论。规则工具要遍历当前供应商已成功处理的所有适用证据；只有需求、报价、规格书相关覆盖完整时，才能认定某字段缺失。检索无结果只表示“本次没有召回”，不等于原件没有写。

**生成与校验。** 给模型的每块上下文都带稳定 evidence ID 和原件位置。最终答复中的引用必须回查原文、文档版本和工具结果；没有足够来源时明确说无法核实。记录检索查询、过滤条件、候选 IDs、排序分数和最终采用 IDs，供误判复盘。

## 5. 首个验收切片

使用 `examples/dev-pack-001/`，提问“供应商 A 是否满足采购需求？”：

- 确认 Agent 仅检索当前 Case 的三份文档、当前版本；追问“内存为什么冲突？”能沿用同一供应商/字段上下文。
- 真实 Provider 有实际 API 调用记录；Fake Provider 可在 CI 重放工具选择。工具轨迹包含检索及规则调用；正式状态与规则结果一致。
- 八字段答复所引证据能回到 PDF 页码/bbox 或 XLSX 工作表/单元格。开发样例中的 16 处标注证据可用作初始定位检查。
- 测试故意遗漏一个检索关键词、替换文件版本或让模型返回虚构 evidence ID；系统不得把检索漏召回当成“证据不足”，不得引用旧版本或虚构来源。

模型 Provider、token 预算、检索 top-k 和是否引入向量召回，在真实模型选定后以开发集结果定值并记入环境/评测报告。
