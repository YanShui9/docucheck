# M3-11c：人工事实修正后的确定性复核

日期：2026-09-29。用户已确认只修正有原文支持的提取事实，并在 M3-11b 提交修正后继续本步。目标是在新快照形成可复核的规则结果，不调用模型、不改变原件。

## 方案取舍

采用“映射已验证事实并重跑现有规则”：将来源 Run 的整组事实逐项映射到新快照，保留旧事实并加入新值，重新验证每项原文后调用 `evaluate_field` 或 `evaluate_memory`。用户已确认：同一原文同时支持旧值和新值时保留冲突、标记需人工复核。重新调用模型会产生费用和不稳定抽取；让人工直接填写业务状态会绕过规则与证据约束。因此本步沿用现有事实和规则契约。

## 数据与 API

新增 `correction_reviews` 追加表，以 `correction_id` 为唯一键，保存新快照的事实集、被修正事实 ID、`CheckResult`、处理状态和时间。`POST /api/v1/cases/{case_id}/corrections/{correction_id}/recheck` 同步执行一次，重复请求返回同一结果；`GET` 修正审计增加 `review_status`、新事实和规则结果。复核前先读取当前 Case、修正记录和来源 Run；计算在短事务外完成，提交时锁 Case 再核对版本和唯一键，防止与上传或并发复核竞态。已有复核可在后续 Case 版本中作为历史记录读取并重复返回。

## 证据与失败边界

复核重验来源 Run 的 v2 事实集、审计中的旧事实和新候选，以及新旧证据 ID 的确定映射、文本、角色、供应商、哈希、解析版本和位置。所有同组事实均需重新通过原文校验，不只检查被改的一项。字段、型号、限定语、比较符、计价口径与单位归一化仍由现有提取校验与规则决定。任何映射、来源或审计不一致均拒绝，且不写复核结果。

如果原事实集的完整扫描标记为 `false`，或新快照覆盖不完整，规则结果必须为 `partial` 且 `business_status=null`。完整扫描时现有规则可以产出业务状态，但修正记录仍为 `needs_review`：旧值和新值均有同一原文支撑，不能仅靠一次人工输入消去矛盾。当前正式上传资料没有可靠的产品型号绑定，现有规则会保守返回“待人工确认”；本步不猜型号或放宽规则。

复核结果只说明该次人工修正的确定性重算。新快照的 Agent 运行仍被阻断，因为 Agent 的抽取工具尚未采用修正事实，放开会出现答复与复核不一致。将修正事实接入后续 Agent Run 是单独任务。资料上传生成更高版本后，旧复核保留为历史记录。
