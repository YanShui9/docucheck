## 3. 本机条件与 Milvus 部署决策

### 3.1 已查明的本机事实

现阶段不能说“Milvus 已部署可用”。已有退出日志包含 etcd 信息，但本轮未定位退出根因，不据此断言一定是缺少某个组件。没有覆盖旧实例、删除卷或读取/输出保存的连接密码。

Attu 2.6.4 的版本 README 中兼容表仍推荐 2.6.x 对应 Attu 2.6.3；2.6.4 为同系列后续版本。可作为现有连接候选，具体 SDK/服务端/Attu 组合需要实际验证，不能直接宣称完全兼容。新的 Attu main 已是 3.x，实施时按版本固定文档，避免混用。

### 3.2 推荐：Milvus Standalone，优先验证官方嵌入式单容器形态

Milvus Standalone 是单机服务部署；单容器嵌入式方案仍需配套配置和持久化目录。优先按选定 2.6 补丁版本的官方安装资产核对 embedded etcd、存储配置、端口和健康检查，降低本机要维护的独立组件数。官方 Compose 的独立 etcd/MinIO 形态作为需要相应能力或排障时的备选；不把一个裸镜像等同完整配套安装。

不直接升级或复用旧实例的数据目录。先检查旧挂载、版本、数据保留需求和启动失败原因，再决定隔离新实例还是恢复现有实例；新应用集合采用明确命名空间。安装资产、服务端、pymilvus、Attu 和 schema 版本写入复现记录，不能使用未固定的 latest 标签。

官方 2.6 要求页列出 Standalone 至少 8GB、推荐 16GB 内存；本机 Docker 当前可见内存约 7.38 GiB，尚未满足这项最低资源条件。实施前需要评估单套项目栈、Docker/WSL 内存和宿主保留空间，或者选择独立机器/托管 Milvus。本轮不自动停掉任何已有服务、不修改 Docker 设置，也不承诺该硬件一定能同时承载所有服务。[官方资源要求](https://milvus.io/docs/v2.6.x/prerequisite-docker.md)。

Attu 用于查看集合、索引、数据和检索，业务服务通过 pymilvus 直接连接 Milvus。应用工作不依赖 Attu 是否打开；Attu 不负责生成本项目上下文或保存业务记忆。管理员的向量修改不能代替应用中的事实修正和审计。

本机桌面 Attu 在默认回环映射下连接 127.0.0.1:19530；实际地址格式以 2.6.4 界面为准。容器 worker 使用所选 Docker 网络中的服务名，不用容器自己的 localhost。认证/RBAC、仅内部可达的端口、持久化及必要 TLS 在部署阶段一起配置。

Milvus Lite 可用于独立实验，但主联调要验证服务端连接、索引就绪与跨进程行为；Distributed/K8s 暂无规模需求。Standalone 的单机故障仍会中断语义检索，不能宣称多副本高可用。

### 3.3 Embedding 与本机资源

保留本地 BGE-M3 基线，先验证已有 GPU 是否能被隔离的 Embedding 进程实际使用；有 GPU 不等于当前 Python/Docker/CUDA 组合已经可用。避免把 PyTorch/模型依赖混入现有主环境造成锁文件冲突，运行形态在小探针后固定。

初始并发为 1、限制输入分块和小批量，测试与 MinerU 共存的显存及内存；不把 Milvus 本身切到 GPU 索引。模型调用仍可使用已有 DeepSeek Provider。若本机资源或召回不达标，保留独立云 Embedding Provider 选择，但接入前说明发送内容及费用，不假设聊天 API 能提供 embedding。

## 4. Agent 方案比较

| 方案 | 优点 | 对本项目的限制 | 决策 |
| --- | --- | --- | --- |
| **单 Agent + 受控业务子图** | 自然聊天/动态查资料；正式审查覆盖、预算和状态可由代码验证；复用现有组件 | 需设计意图、类型化计划和子图边界 | **推荐** |
| 单 Agent 自由 ReAct 循环处理所有任务 | 实现初期入口简单，可按观察调整 | 大规模矩阵反复规划可能漏项、耗费调用；现有 graph.py 已出现专用矩阵逻辑 | 保留给有界资料问答，完整审查进入批处理子图 |
| Supervisor + 多专业 Agent | 可拆分独立长研究，获得不同上下文和并行探索 | 本项目没有已证明收益；增加调用、状态协调、权限传递和失败归因成本 | 后续只有实测需要时引入 |

采购助手仍是 Agent：模型可以判断需要哪些资料、选择检索/读取工具、解释不同口径并提出澄清。正式规则、用户权限和全量覆盖由服务端控制。LLM 的灵活决策与可验证的流程组合，是本项目的架构选择。

软件形态采用现有 FastAPI 模块化应用 + 独立解析/索引/审查 worker；MySQL 为业务权威，Redis 承担队列/有期限缓存，Milvus 承担语义索引，Attu 为管理客户端。保留 LangGraph/LangChain 与现有 Provider；不同时引入 CrewAI、第二套队列或额外关系数据库。

解析、向量化、事实抽取、规则比较是职责明确的服务/节点；调用了模型的抽取服务不因此自动成为一个有独立规划/记忆的 Agent。首版并发靠可控任务批次，不增加“采购专家/食品专家/质检专家”角色轮流讨论每一格。

## 5. 顶层编排和节点契约

### 5.1 一轮请求的路径

鉴权与装配上下文 → 理解意图/范围 → 按需选择以下路径 → 验证产出 → 提交消息/有效状态 → 异步摘要。

| 路径 | 执行方式 | 完成/暂停条件 |
| --- | --- | --- |
| 普通聊天/能力说明 | 无必要资料时直接回答；不要求先创建资料快照，不强制 tool call | 保存真实聊天答复；不能凭空给某供应商正式采购结论 |
| 资料问答 | Agent 选择检索、读原文或读取已有结果；有界工具循环 | 引用回读验证后回答；对象不明则集中澄清 |
| 整理清单 | 调用候选抽取/用户要求规范化服务，生成有来源的草稿 | 用户确认清单版本后才进入正式审查 |
| 局部/完整审查 | Agent 提出目标范围，服务端生成并验证批次计划，执行审查子图 | 范围、覆盖与规则全部符合后提交；缺失/冲突/待人工状态按契约报告 |
| 来源追问 | 按有效版本直接读取已验证结果/原文；必要时补检索 | 不为展示已保存结果重做整套规划；资料或要求变化后明确历史范围 |

已有显式命令/页面动作优先确定路由；自然语言无法确定时，模型返回有类型的动作或正常答复。尽量把“理解意图＋回答/选工具”放在同一次调用，不设计每条消息必须依次经过路由模型、规划模型、审稿模型。

普通答案允许无工具的正常 content；工具动作按 schema 校验。正式审查必须由受控结果提交路径生成，不能为了兼容普通聊天放宽全部答案的事实/引用验证。

### 5.2 状态与计划

顶层状态包含：会话/消息序号、route、当前焦点、资料/清单/任务记忆版本、待确认问题、计划 ID、工具观察 handle、实际/预留用量和运行状态。实际资料/事实放在服务端仓库，通过 handle 引用。

审查计划包含：目标品目、供应商、已确认 criterion_id 集合、适用 document_id、所需覆盖、批次划分、规则/抽取版本、预算及依赖。scope 由授权服务复核；计划 ID 不授予新权限。

计划是可执行的业务简报，例如“按清单第 3 版核验两家大米供应商，先检查报价和交付承诺，再汇总缺项”；不记录或展示模型原始思维链。页面进度来自实际执行事件。

“标准/完整”表示业务覆盖与预算策略；Provider 原生 reasoning 能力另行按模型和接口验证。现有 config.py 对相应 Provider 关闭 thinking，不能把 thorough 模式说成已经启用原生推理模式。

### 5.3 清单和正式审查子图

清单子图：确认文件角色/品目 → 批量抽取需求或订单候选 → 验证来源/单位/规则支持 → 合并明确用户修改 → 展示变更及冲突 → 等待用户确认 → 保存不可变清单版本。

审查子图：验证确认版本/容量 → 枚举适用资料与所有目标格 → 组装原文批次 → 抽取多个相关指标 → 校验事实 → 记录覆盖/保存批次 → 确定性规则判定 → 聚合结果 → 验证引用与完成状态。

目标矩阵先由程序列出，批次不会由模型任意跳过。批次可以处理多个指标，规则比较不新增模型调用；范围变化需要显式重新验证计划。计划不能仅凭 RAG 的 top-k 来宣布全部资料扫描完成。

## 6. 工具、错误、停止与恢复

### 6.1 工具边界

保留检索、读原文、抽取、规则、读取结果等现有能力，增加独立的草稿/确认/记忆仓库接口。工具 schema 使用动态 criterion_id 和有限规则类型，服务端注入身份、任务/快照与版本；模型参数不能覆盖这些值。

工具返回有类型结果：数据 handle、source_refs、覆盖/版本、状态以及可恢复错误。权限错误、schema 错误和真实业务缺项有不同处理，不把技术错误转换成“证据不足”。写入操作具有幂等键、确认条件和版本检查。

“记住我的回答偏好”和“改变采购要求”分别写入个人记忆和清单；改变要求不能修改供应商事实。发布/删除等有影响的操作依据用户明确动作及已有权限执行，模型读到文档里的指令不构成授权。

### 6.2 有限循环与预算

- 普通聊天无需工具循环；初次资料问答与弱召回改写最多两次检索尝试，更多需求由明确新问题/预算规则处理。
- Agent 对新增观察决定是否继续；同样参数/版本的重复调用命中缓存或返回重复提示，避免不断获取同一资料。
- 正式审查计划由服务端执行，允许一次针对性补抽取或受控范围修订，随后按真实完成状态返回；不无限重规划。
- schema/结构化结果修复初值最多一次；网络暂时故障有短次数重试与退避，但所有请求共享调用、token、时间和取消预算。
- 独立统计规划/路由、抽取、解释、摘要和 Embedding 用量。Provider 返回的实际 tokens 与保守预留分开；未知调用用量保持未知，不用估计账单冒充实付金额。
- 限流、超时、向量不可用、容量不足和无法归属分别有中文原因。未审完仍可展示已完成格与待处理范围，整体保持 partial。

以上为实施初值，保持参数可配置并用失败样本校准；不能为了演示成功不断增加预算或把失败当通过。

### 6.3 采用 MySQL 业务恢复及批次检查点

新增审查批次进度持久化，绑定 run/计划、资料/清单/规则/抽取版本、批次 ID、输入指纹及有效完成状态。抽取/验证后的结果和覆盖记录在短事务中登记，更新需要当前 attempt/fence 和预期版本。

重启/重试时重新授权，再读取已经完成且版本匹配的批次，继续剩余工作。迟到 worker 不能回写覆盖新进度；取消、权限撤回、资料或清单变更需要阻断旧计划。并行批次首版默认低并发，结果按稳定目标顺序聚合。

澄清/确认先保存待确认内容和版本，再返回 waiting_user；用户回复通过 API 关联并校验版本后继续。首版用已存在的 MySQL 业务暂停/恢复机制，不依赖内存里的暂停对象。

LangGraph checkpointer 的逐节点重放与这些业务检查点是不同层面的能力。首版承诺跨进程会话/澄清恢复及有效批次复用，不承诺在模型输出的任意 token 或任意节点精确续跑。若将来接入 checkpointer，需数据库实现、序列化、线程授权和 fence 集成的专门测试；不为了采用某个示例立即增加 PostgreSQL。

外部模型请求可能已计费但响应未保存，网络中断后重试无法保证供应商只执行一次；保存请求/响应状态与未知用量，限制重复成本。对业务提交可做幂等，对外部调用不声称 exactly-once。

## 8. 实施顺序及验收

保持四个大步骤，不重新拆成几十次用户确认：

1. **设计/契约定稿**：本轮调研及机制修订；Milvus 已由用户选定，其余推荐与前端视觉以相应草案审阅为准。
2. **后端机制与动态指标**：先资源/连接小探针，再实现聊天/记忆、有界 RAG、Milvus 索引、动态清单和受控审查子图；模块分别验证后一起回归。Docker/依赖/模型下载与 API 操作前说明步骤。
3. **聊天前端**：执行已确认规范，连续聊天、内联上传与清单确认、按需成果面板；此前的前端讨论约定保留。
4. **多品类联调验收**：设备与包装食品、故障恢复、权限、引用、用量与性能；明确开发集和独立资料集边界。

第二步的最小验收路径：无资料普通聊天 → 上传需求/订单并生成确认清单 → 上传两家资料 → 同义问题经 Milvus 命中原文 → 完整审查 → 来源追问 → 重启恢复 → 更改清单后保留旧报告。

故障验证包括：Milvus 未启动、索引未加载/写入未可见、Embedding 超时/维度错误、过滤字符串注入、越权来源、覆盖缺块、旧 worker/迟到摘要、批次完成后强制中断、等待用户时版本变化，以及删任务但物理向量仍存在。

性能对照分别运行 BM25 与 BM25+Milvus；质量报告相关证据召回、逐格结果、引用和危险满足，性能报告冷/热解析/索引/问答/完整审查、规划/抽取调用数与资源峰值。不能用单次顺利演示替代这些成果。
