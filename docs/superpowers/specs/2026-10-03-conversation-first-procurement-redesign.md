产品目标：用户直接说需求、上传资料、提问和追问；助手根据意图使用资料和工具，整理可确认的审查清单，再产生可追溯的结果。采购任务承担资料与权限边界，聊天承担主要交互。正式核验需要明确的采购要求及有效证据；日常问答不要求先上传文件。

现有笔记本八字段成为一个兼容模板。新的通用框架以品目、指标和规则类型扩展，逐品类验证能力；已有设备开发集成绩仅覆盖原场景。

## 4. 中文操作流程

### 4.1 从聊天开始

首页显示“你好，今天要核对什么采购资料？”，配一个主要输入框和少量示例：“解读采购需求”“对比供应商”“整理审查清单”“查找资料冲突”。用户无需先理解项目、Case、会话、Run 或快照。

允许直接问“你好”“你能做什么”“我需要准备哪些资料”；只上传需求时，允许解读需求和整理指标。只有用户要求供应商核验、且缺少适用资料时，才说明缺少哪份资料。个人日程、未提供的历史活动等无数据问题，直接解释信息范围，不捏造记忆，也不无关地追问供应商。

### 4.2 上传、确认、审查

1. 用户在对话输入框添加文件，文件卡片显示上传和解析状态。
2. 助手建议资料角色、供应商和品目；用户确认绑定后才进入正式审查范围。文件名推断及模型建议不能自行确定业务归属。
3. 用户可直接设置指标，也可从需求、订单整理候选清单，或结合模板修改。助手展示来源、品目和口径，用户集中确认；只对歧义或冲突追问。供应商报价不能自行变成买方要求。
4. 用户说“比较这两家的报价”“按需求完整审查”，或点击一个明确动作；助手选择相应工具。
5. 对话中给出短结论、风险、需要补充的信息和可点击来源，并提供“查看对比表”“查看原文”“导出报告”。
6. 用户继续追问，保持同一任务上下文；替换资料或改变审查要求会产生新版本，旧报告保留。

供应商为采购对象的供应商；页面显示已登记的中文名称。不会将演示中的 vendor-a 作为所有用户的业务用语。

### 4.3 中文名称和输入规范

| 当前用语 | 用户界面用语 |
| --- | --- |
| Case+ID | 用户命名的“采购任务”，如“食堂大米采购” |
| Run | “本次审查”或“处理记录”，次级详情可查技术 ID |
| Snapshot | “资料版本” |
| supplier handle | 供应商登记名称；ID 仅用于内部关联 |
| 八字段核验矩阵 | “供应商对比”或“审查结果”，按本任务指标生成 |
| JSON / XLSX 主按钮 | “导出报告”，提供 Excel；JSON 收入开发详情 |
| agent_model / agent_tool / reason_code | 清楚的处理步骤及错误原因，技术详情可展开 |

中文输入法组词时 Enter 不发送；默认 Enter 发送、Shift+Enter 换行。复制、Markdown、表格、长文本和来源跳转均有明确反馈。日期按中国时区展示，金额标明币种和计价单位，规格/单位不做隐式换算。登录界面也应采用中文，保留真实 OIDC 认证。

## 5. 普通聊天、资料问答、审查与上下文

### 5.1 分开处理用户意图

| 路径 | 需要的资料 | 产出 |
| --- | --- | --- |
| 普通对话 / 能力说明 | 可无资料 | 正常聊天、解释使用方法、采购讨论；不产生正式判定 |
| 资料问答 / 摘要 | 用户可读取的任务资料 | 带原文引用的解释；总结范围不足时明确说明 |
| 清单整理 | 需求、已确认角色的订单或用户明确要求 | 有来源及版本、待确认的结构化审查要求 |
| 核验 / 对比 | 已确认的清单和适用供应商资料 | 有证据及规则版本的审查结果 |
| 澄清 | 当前任务确实缺少必要信息 | 一个明确问题；回复更新任务状态，转向新意图时重新路由 |

普通聊天无需强制每轮工具调用；资料问答使用有界工具循环，完整审查进入由服务端枚举目标与覆盖的审查子图，保存版本化批次进度后执行规则。帮助询问不能误入“缺供应商”的流程。界面用连续消息展示过程，后台执行记录作为可展开的详情。

### 5.2 上下文分层

- **上下文装配**：服务端先校验身份及任务权限，再装配系统约束、本次问题、任务/清单版本、当前焦点、摘要与最近消息、必要原文及验证结果。按 token 总预算裁剪可选信息，不裁掉当前问题和权限边界。
- **会话记忆**：MySQL 保存完整消息与有覆盖范围的摘要；近期消息直接读取，旧消息按同会话范围查回。摘要后台更新，原始消息仍可查看。
- **任务记忆**：MySQL 保存用户确认的目标、品目、待确认事项与清单版本；新会话关联同一任务后，按权限恢复。
- **个人记忆**：用户明确要求保存的回答偏好、常用模板，按 OIDC 用户身份隔离，可查看、修改及删除；不会自动把某个任务的价格或供应商结论用于其他任务。
- **证据及结果**：原文、事实和结果仍由服务端按资料及规则版本读取；摘要、偏好与以前的模型答案不能充当供应商证据。

切换任务、账号、品目或资料版本时分别处理权限与事实失效。记忆保存需要来源、版本、乐观锁和运行栅栏，失败或过期执行不能覆盖最新记忆；用户修正与版本更新需要重算。模型内部思维链不作为记忆保存内容。

普通对话可以先创建属于当前用户的会话；关联采购任务后才注入该任务权限下的资料。不能为了绕过现有快照要求而给空白聊天捏造资料快照。

### 5.3 RAG 的改进

**向量检索已纳入明确设计范围，用户已指定 Milvus，推荐 Standalone + 独立 Embedding 服务 + 现有 BM25Plus 混合检索，使用已有 Attu 管理。** MySQL 保存权威原文、业务数据和记忆，Milvus 保存可重建的原文向量索引，Redis 保存有期限的缓存/队列状态。模型提出检索需求，服务端绑定权限和版本过滤，不能由模型自由指定账号或越权范围。

Embedding 推荐先验证本地 BGE-M3，固定模型修订、维度及分块版本；硬件性能未实测，不能提前承诺速度。支持独立的云端 Embedding Provider，但不默认当前 DeepSeek 聊天配置包含向量接口。安装、模型下载或 API 接入前提供具体步骤及费用/资源说明。

解析完成后通过持久化索引任务异步分块、批量向量化及幂等入库。问答时词法/向量各召回一批候选，在应用层按排名融合、去重并读回原文；重排是否加入由质量与延迟评测决定。索引核对加载状态及 Strong 可读性后才标就绪，保留失败/重试状态；SQL 与向量库之间采用可恢复的最终一致性，不声明跨库原子提交。本机旧 Milvus 已退出，资源与连接验收尚未完成。

资料问答按相关性检索；完整审查按适用资料全量覆盖。top-k 未找到内容不等于文档缺少该指标。检索输入不包含 gold；新资料和账号之间不能复用越界缓存。

## 6. 多品类动态审查清单

### 6.1 从需求决定指标

“八项”不作为通用产品上限。支持三种入口：手动设置、从需求/订单识别、模板与自动识别结合。用户可通过对话说“加一项含税单价不超过 120 元/袋”，也可在清单面板新增、修改、停用指标并保存模板。模板提供建议，最终要求由用户确认；没有要求时，不擅自生成强制业务标准。

自动识别先确认文件是买方需求、买方订单、供应商承诺还是其他资料，再按品目抽取指标与来源。需求与订单的数量、价格或交期不一致时保留两个来源，由用户确认适用要求及变更原因；不按文件名、上传顺序或模型猜测覆盖。仅有订单也可整理其明确的采购要求，不能自动补出没有写明的标准。

用户手写要求记为“用户设置”并关联确认消息/操作；文档抽取要求关联原文定位。设置采购要求与纠正供应商提取事实是两种操作：后者继续要求原文支持，原文同时支持两个值时保留冲突。用户新增要求也不会反写原件或抹除历史结论。

| 示例品类 | 可能的指标，实际以需求为准 |
| --- | --- |
| 笔记本设备 | 内存、容量、屏幕、重量、质保、数量、单价、交期 |
| 包装食品 | 品名/等级、净含量、包装规格、保质期、生产日期、交付时剩余保质期、数量、计价口径、交期 |
| 办公耗材 | 材质、尺寸、型号适配、包装数量、单价、交期 |

食品清单来自采购要求，不能凭模板宣布食品安全、资质真实性或行业合规已验证。涉及专业标准时，需要适用标准的来源和版本，以及已验证的规则支持；超出能力的规则标为待人工确认。

### 6.2 有边界的规则框架

每条指标包含稳定 ID、中文名称、适用品目、类型、比较方式、要求值、单位/口径、文档或用户设置来源、确认状态、清单版本及规则版本。指标 ID 与名称分离，同名但不同品目/口径的指标不能合并；草稿需要确认后才用于正式审查。

先定义有限、可验证的规则类型：数值上下限/区间，金额及计价单位，枚举/文本属性，资料存在性，日期/期限。日期规则还需比较基准、日历/工作日口径及必要时的生产/交付日期；基准不明时必须澄清。

模型提出候选要求和事实；服务端验证原文、归属和规则参数，再由受控规则执行。自定义指标不是任意 Python/SQL 表达式，不让模型生成可执行代码。审查清单的改变形成新版本，并绑定到运行结果。

动态指标仍受资料数量、上下文、调用和时间预算约束。执行前进行容量预检，必要时按品目分批；未完整覆盖的指标不得标为正式完成。当前文件格式与解析上限不因改版自动放宽。

同任务多品目按品目比较：同一供应商的大米与食用油分开；袋、桶、箱、公斤的数量和单价只有明确包装换算后才能比较。不能把不同品目或计价口径放入同一个数值判定。

### 6.3 现有代码的迁移

需要同步调整字段契约、抽取、规则、Agent 工具 schema、结果接口、持久化和前端，不能只增加食品标签。保留解析、证据校验、权限、异步执行、幂等和审计机制。

旧八字段模板及 `fields-v4` 历史报告通过兼容读取继续使用；旧结果不会被重新解释成新动态指标。新清单类型由服务端限制，数据迁移和导出版本必须有兼容测试。

### 7.2 推荐的具体样式，待确认

- 浅色极简：主内容白色、侧栏浅灰、正文深灰；深蓝只用于主动作/选中状态，业务状态颜色克制。
- 中文系统字体优先，正文约 16px、行高约 1.7；标题 24–28px。避免把信息缩到小字，以中文内容长度检查布局。
- 对话区域约 760–880px 的舒适阅读宽度，主输入框置于对话底部；空白会话显示居中的欢迎区。
- 桌面侧栏约 240px，可折叠，显示“新建对话/采购任务/最近对话”。中文任务名称取代裸 ID。
- 资料、清单、对比、原文放在按需打开的详情区；打开对比时允许宽视图。无需一开始就呈现三栏和长矩阵。
- 1024px 以下收起侧栏，768px 以下详情作为全屏面板；侧栏与细节面板不要挤压正文成窄列。
- 助手答案支持 Markdown、来源标签、结构化结果卡片。默认简短总结，再提供表格和原文入口。
- 加载、解析中、等待确认、重试和错误都有中文说明。进度显示真实执行步骤，不模拟内部思维。
- 轻量边界与少量阴影建立层级，减少多层卡片/边框、技术说明常驻和过多独立按钮。

## 9. 最低验证清单

- 无文件输入“你好/你能做什么/怎么用”：正常回答，不能报工具数量错误或强制索取供应商。
- 仅上传采购需求，询问“讲清楚我的要求”：正确解读并引用需求，不要求先有报价。
- 询问“按这些要求比较供应商”：使用已确认清单，缺资料只提示具体缺项。
- 食品任务有不同于设备的字段数及日期/规格指标，页面和导出使用同一清单版本。
- 价格按公斤/袋/箱混合时，未经明确换算不得比较为达标；跨品目、供应商和版本不串证据。
- 长对话压缩后保持焦点与待确认信息，但不得用摘要代替原文证据。
- 服务重启后完整消息、摘要、用户确认的偏好及清单版本可恢复；旧执行不能覆盖新记忆，删掉的记忆不会由摘要/缓存再次召回。
- 手动设置指标、从需求/订单识别及两者结合均可用；缺失单位/品目和来源冲突需要确认，无原文的用户要求标清作者，不伪造引用。
- “什么时候到货”等同义问法可经向量找到“交付期限”；混合检索留有排序与来源记录，跨账号/任务/品目和过期索引不得进入模型输入。
- 资料更新、清单更新及人工事实修正后历史保持只读；原文同时支持两个值仍保留冲突。
- 中文输入法回车组词不会发送；常见屏宽下文字与主要动作可读且没有挤压溢出。
- 普通聊天可流式展示；审查中的阶段和结果只显示已完成的实际事件，失败时不伪造完成。
- 原有设备场景、来源定位、OIDC/Case 权限和运行恢复回归继续通过；新增食品样本独立列示成绩。
