## 2. 已完成的修复

### 2.1 Docker worker 的 HTTPS 信任

旧 HTTPX 与 HTTPX2 均复现证书校验失败，错误码19。TLS 链包含本机 Kaspersky 公开根证书，经 SHA-256 与 Windows 已受信任根证书核对一致。因此没有把错误直接归因为 SDK 或 Celery fork。

把容器原有公有 CA 与已核对的本机公开根证书合并，仅对本机 worker 只读挂载并设置 `SSL_CERT_FILE`。未关闭证书校验、未取私钥、未改变 Windows 防护配置。两种客户端的冷进程/冷 fork 空请求均得到预期422；空请求不提供模型或消息，不触发推理。真实上传预跑随后完成。

配置符合 [Docker 对 HTTPS 检查代理证书的说明](https://docs.docker.com/engine/network/ca-certs/)及 [HTTPX 的证书环境变量说明](https://www.python-httpx.org/environment_variables/)。这份本机 CA 覆盖配置不能直接当作企业部署配置；不同机器应使用其实际信任体系。

证据：`data/m5-local-tls/certificate-provenance.json`、`transport-comparison.json`、`prefork-transport.json`。本机组合 CA SHA-256 为 `3a1fbef8757f29e99c69ff68c4da91b8412f562e4dbed865ce21c8ea0dae3f5c`。

后续本机同步 worker 必须保留已核对的覆盖文件，否则普通 Compose 重建可能移除该配置：

```powershell
docker compose -f compose.yaml -f data/m5-local-tls/compose.tls.yaml build worker dispatcher cleaner
docker compose -f compose.yaml -f data/m5-local-tls/compose.tls.yaml up -d --no-deps worker dispatcher cleaner
```

同步前检查当前快照的待解析任务及活跃 Run。本轮没有启动或修改前端。

### 2.3 失败诊断落库

原 Run 只落库 queued/claimed/finished，丢失模型和工具的细分失败。增加安全 `agent_model` / `agent_tool` 事件，与 Run/attempt 完成在同一事务写入，旧领取者不能追加。

只记录固定工具/操作名、白名单错误、字段覆盖类别、受校验的计数与用量。历史数量有上限；不保存原始提示、工具参数、原文、认证信息或任意错误字符串。事件时间是完成时的持久化时间，不能当作实时流或每个步骤的耗时。

实际新 m5-c01 Run `7a3b9fec74c24013acd664acb9e52356` 在 MySQL 写入7条安全模型/工具事件，错误为 `fact_field`。由于原模型候选未保存，仍不能断言具体哪个候选导致失败。已通过隐私过滤、类型边界、旧领取者拒绝及事务回滚测试。取消过程的完整模型轨迹及真实取消时延仍未测量。

参考 [LangChain 结构化输出错误处理](https://reference.langchain.com/python/langchain/agents/structured_output/ToolStrategy)核对验证和恢复设计。当前补齐的是诊断；没有因此增加不受预算约束的自动重试。
